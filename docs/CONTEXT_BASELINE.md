# 开工前先看这里

现在仓库里只有产品规划和说明文档，还没有能安装使用的应用。可以先做原型、比较技术方案，但有几件事需要在正式实现前说清楚。

## 先从哪里开始？

先看 [README](../README.md)了解项目，再看[开发计划](ROADMAP.md)确定这次要做哪一步。具体功能、权限和验收要求，按[产品需求](PRD-v0.5.md)里的 FR、AT 编号查找。

开始一个任务时，写清楚要解决的问题、完成条件和暂时作出的假设。文档、Issue 或图片说法不一致，就先讨论并更新说明，不要因为某一份更新得晚，就自动把它当成最终决定。

目前确定的是：文档使用中文，项目放在 demble-team 组织下，源码采用 PolyForm Perimeter 1.0.1。语言、框架、数据库、模型厂商、部署办法和命令行名称都还没选定。

## 还有四件事没定

下面的 OD 编号对应产品需求第 16 节，集中跟踪在[任务 #12](https://github.com/demble-team/demble/issues/12)。它们不是本次自检替团队选好的答案。

### 1. 移除成员后，旧内容怎么失效？（OD-11）

`context_revision` 记录的是正式项目内容的版本。成员被移除、令牌被撤销，不一定会改动这个版本号，因此不能只看版本没变就继续返回旧缓存。

每次请求仍须按当前权限检查。缓存怎么清理、哪些变化需要同步，要在 S0 的权限设计和 S3 的接口实现中确定。已经交到外部客户端的数据，也不能承诺可以远程收回。

### 2. 一次审核十条建议，其中一条冲突，怎么办？（OD-12）

可以整批拒绝，也可以让用户明确拆成两次提交，但不能界面显示“全部成功”，实际只保存了一部分。

在 S1 实现前，要说清楚一次提交包含哪些改动、生成几个版本，以及失败后重试会不会重复写入。

### 3. 反馈和证据究竟对应哪个版本？（OD-13）

大家评价的是当时看到的 Demo，不是链接后来更新后的内容。同样，决定引用的一条消息被编辑后，也不能让原来的证据跟着悄悄变化。

需要确定原始内容和成果版本如何标识，如何引用，删除后显示什么。来源部分在 S0 确认，成果和反馈部分在 S2 确认。外部 URL 或正在运行的服务，也不一定能当作固定的内容快照。

### 4. 分给某人的任务，算不算他已经接受？（OD-14）

“有权安排任务”和“本人已经接受”是两件事。有权人能不能代为接受、系统怎样记录，还没有定。

在做 S2 的任务和责任状态前，要把这些状态和操作权限区分清楚。AI 不能因为一句含糊的话，就认定某人承诺负责。

除此之外，原来 OD-01–OD-10 的问题仍按[产品需求](PRD-v0.5.md)保留为待讨论事项，尤其是确认权限、重大分歧和编程工具可直接提交哪些记录。

## 两张图应该怎么看？

首页介绍图用来解释使用场景；架构图用来说明权限检查和审核流程。方框不代表要拆成独立服务，也没有决定用哪种数据库。

图里没有画出所有功能。例如 AI 也可以被邀请参与讨论；成果和进展的上报，不等于自动修改正式决定。

“原子提交”要求不要把不完整的保存说成成功。一次提交的范围和具体事务办法，还要按 OD-12 讨论。读接口时同样要检查权限，不能因为图里有一条返回箭头就绕过去。

字段表、命令和 JSON 也都是示例；不要直接照着建表或把它们当成完整 API。
