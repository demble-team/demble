# 开发计划

Demble 还没有完成任何一个阶段。我们准备从三个人能实际使用的版本开始，逐步验证它是否真的减少了沟通和重复解释的工作。

下面的 S0–S4 表示验证顺序，不是已经承诺的工期。技术栈也还没确定。

## S0：先让三个人用起来

先做成员邀请、项目空间、实时聊天和消息引用。会议先支持语音、屏幕共享和手工纪要，不依赖外部聊天或会议账号。AI 可以暂时不接入。

做到三个人能完成一次讨论和会议，并验证空间外的人读不到私有内容，就可以评估这一步是否可用。

## S1：把讨论整理成有依据的决定

接着做待审核的建议、批量确认和修改记录。AI 可以帮忙找出可能的决定，但是否采用、怎么修改，由有权限的成员确认。

检查的重点是：决定能查到原话或纪要；被替换的旧决定仍有记录，但不会继续作为当前要求返回。

## S2：比较两个 Demo，再决定方向

为实验记录问题和判断标准，允许不同成员同时尝试不同方案。先支持现有链接和静态 Demo，反馈要固定到大家当时体验的版本上。

让两位开发者提交两个可体验的方案，其他人留下反馈，再据此调整计划。本地动态预览可以先做可行性和安全验证，不能未经验证就承诺所有网络都能访问。

## S3：让不同的编程工具读到同一份项目背景

提供命令行和 HTTP API，让成员自己的 AI 编程工具读取已确认的决定、当前任务和相关资料，并提交进展与成果。

至少用两种工具验证：相同权限下读到的有效决定一致；未确认建议不会被当成正式要求；结果能关联到正确实验。权限撤销和旧版本提示也需要测试。

## S4：连续用两周，看看哪里还费劲

找一个真实团队持续使用，记录缺席成员恢复进度、审核建议、从讨论做到 Demo 各花了多少时间。

根据实际问题改进摘要、去重、搜索、AI 参与讨论和故障恢复，不靠增加功能数量判断项目是否有价值。

## 现在可以从哪里开始？

先读[开工说明](CONTEXT_BASELINE.md)，再从 [S0 任务](https://github.com/demble-team/demble/issues/1)讨论成员权限和原始记录的设计。详细需求和验收编号保留在[产品需求](PRD-v0.5.md)中。

首个阶段不做完整视频会议平台，也不做自主运行和调度编程工具的系统。Demble 不替代编辑器，不要求成员统一工具，AI 也不能自行确认正式决定。
