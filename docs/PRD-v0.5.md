**版本：** v0.5（全新基线草案）
**日期：** 2026-11-02
**产品阶段：** 需求定义与 MVP 验证
**目标读者：** 创始开发团队、产品设计与工程实现者
**状态：** 可用于原型设计和技术拆解；文末开放问题仍待确认

## 0. 执行摘要

Demble 是面向 2–10 人小型 AI 原生开发团队的自托管共创工作空间。它内建日常群聊与会议能力，连接想法讨论、实验、Demo 体验反馈、团队决策、动态计划和外部 Coding Agent，让成员在不统一开发工具、不依赖微信或飞书等外部协作平台的前提下，以低协调成本把想法快速变成可体验、可比较、可迭代的成果。

Demble 不以托管 Agent 执行为核心。人类负责方向、规划、讨论与正式决策；AI 默认安静地组织信息，在成员主动 @AI 时参与推理和建议。不同成员可继续使用 Codex、Claude Code、OpenCode、DSH 或其他 Harness；Demble 通过开放、机器可读的接口向它们提供经过权限过滤的团队上下文，并接收可审查的开发成果。

**本版核心产品机制是 Context Review（共享上下文变更审核）：** AI 从聊天、会议、Demo 反馈等原始事件中提取、去重和关联候选变化；成员在适当节点批量审核。只有经授权确认的变化才能成为正式决策、计划或任务状态。原始证据和版本历史始终保留。

**首个可验证闭环：** 创建 Room → 讨论想法 → 形成候选决策和实验 → 批量确认 → 两人用不同 Agent 制作 Demo → 分享与反馈 → 对比实验并调整计划 → Agent 读取最新、可追溯的共享上下文。

### 0.1 文档边界

本 PRD 规定产品目标、角色、信息模型、功能行为、优先级、验收标准与阶段计划。它不绑定具体编程语言、数据库或 AI 模型，不替代技术设计文档。旧版 PRD 中未在本轮讨论里明确确认的实现细节，不被视为本版既定约束。

### 0.2 优先级定义

| 级别 | 含义 | 决策原则 |
| --- | --- | --- |
| P0 | MVP 必须具备 | 没有该能力，端到端闭环无法真实验证 |
| P1 | 首次迭代增强 | 有明显价值，但允许先用简化实现验证 |
| P2 | 后续探索 | 验证需求与可维护性后再安排 |
| Out | 明确不在当前产品边界 | 除非重新立项，否则不纳入 |

## 1. 背景、机会与问题

### 1.1 使用背景

几位有想法的朋友会同时使用不同 IDE、Git 工作流和 AI Coding Agent，共同开发尚未确定方向的项目。AI 降低了编码与原型制作的成本，但团队仍需在群聊、会议、代码、不同 Agent Session、Demo 页面和个人笔记之间反复解释意图、同步状态、寻找决策来源、整理任务与恢复上下文。

团队还面临一种新的工作形态：同一个想法可以迅速产生多个技术或交互原型。此时，最需要管理的不是一条固定需求的执行进度，而是“我们正在验证什么、为什么采用这个方向、如何比较真实体验、何时改变计划”。

### 1.2 核心痛点

1. **想法到体验有摩擦：** 创建任务、协调分工、发布预览与收集反馈分散在多处，导致探索成本高。
2. **团队理解不一致：** 讨论结论可能只存在于某次聊天或某个人的 Session；后来被推翻的决定仍可能被引用。
3. **上下文搬运重复：** 每次启动不同 Agent 或新成员接手，都需要人工复制背景与最新变化。
4. **聊天信息密度低：** 原始记录值得保留，却不适合成为每个人的日常阅读界面。
5. **AI 总结缺乏可信状态：** 候选结论、个人观点和团队正式决定容易混淆。
6. **跨工具缺少结果关联：** Demo 反馈、代码版本、实验目标与会议决定无法稳定互相追溯。
7. **现有协作生态带来依赖：** 外部 IM 和会议产品造成数据、权限、链接与接口上的分散。

### 1.3 产品机会

Demble 要把一个团队的“交流—验证—重新规划”形成连续工作流。产品竞争力不来自比通用 IM 提供更多聊天功能，而来自：讨论自然形成可审查的共享知识；实验可以迅速转成真实 Demo；Demo 反馈能够回流到决策与计划；所有成员和 Agent 都能按需获得最新、可追溯的上下文。

## 2. 产品定位与基本原则

### 2.1 定位

**一句话定位：** 自托管、Harness-agnostic、以快速实验和可信共享上下文为核心的小团队 AI 共创空间。

产品的三个面向是：

- **人类协作入口：** Room、群聊、会议、讨论、计划、实验和 Demo。
- **共享上下文层：** 原始证据、正式对象、关系、修订历史、候选审核和按需检索。
- **开发工具接口：** 稳定 CLI／HTTP API；面向支持 MCP 的客户端提供适配器；不控制 Agent 私有 Session。

### 2.2 核心原则

1. **Human-led：** 人类决定目标、方向、规划、授权与验收。
2. **AI-on-demand：** AI 默认不在群里刷屏；后台整理，受邀时参与讨论。
3. **Context-first：** 信息以 Room 的正式状态和证据关系为锚点，不依赖某个聊天窗口或 Agent Session。
4. **Experiment-driven：** 把需要回答的问题和可体验的实验作为一等对象。
5. **Harness-agnostic：** 不限制成员使用什么 Coding Agent；接口不绑定特定厂商。
6. **Low-friction：** 在原始工作位置完成分享、引用和确认；避免新增大量管理动作。
7. **Traceable by design：** 正式结论有来源、建立者、时间、状态和修订记录。
8. **Private by default：** 最小共享、清晰权限；用户本地文件与 Agent 私有会话不自动上传。
9. **Self-hostable：** 日常群聊与会议无需依赖外部协作账号；可以复用开源底层组件。

### 2.3 明确非目标

- 不提供通用即时通讯平台的所有社交功能。
- 不要求团队迁移代码仓库、IDE 或 Coding Agent。
- 不在核心 MVP 内托管 Agent 长期运行、自动改代码、合并 MR 或执行任意本地命令。
- 不把所有聊天消息都自动转换为任务或正式知识。
- 不追求完全自治的 Router、Worker、Watchdog 系统。
- 不承诺使用 AI 就能自动识别真实共识；正式决定需要具名确认。
- 不直接内建完整云 IDE、通用 CI/CD 或任意网络服务的无约束代理。

## 3. 目标用户、角色与权限

### 3.1 主要用户

| 用户 | 日常目标 | 关键需求 |
| --- | --- | --- |
| 小团队发起人 | 推动想法、协调方向 | 当前共识、实验比较、决策确认 |
| 开发成员 | 自由使用自己的工具实现方案 | 上下文包、任务状态、分享 Demo、追溯原因 |
| 体验与反馈成员 | 低门槛参与验证 | 一键打开 Demo、针对版本反馈、无需理解 Git |
| 暂时缺席的成员 | 快速恢复团队状态 | 变化摘要、已确认决定、来源引用与下一步 |
| 外部 Coding Agent | 按授权上下文执行具体开发 | 稳定机器接口、信息版本、可回传成果 |

### 3.2 权限模型

MVP 采用 Workspace → Room 两级成员边界。基本角色为 Owner、Member、Guest；可将“确认正式决策”权限单独授予成员。默认不强制复杂审批链，但确认行为必须记录身份。

- Owner：管理成员、Room 配置、服务凭据、全局策略与删除/导出。
- Member：讨论、会议、实验、Demo、反馈；根据授权确认正式变更。
- Guest：在被明确邀请的范围内查看或反馈；默认不可访问全部历史与 Agent 接口。
- Agent Credential：绑定人或服务账户、Room 范围、最小读写权限、可撤销、可审计。

**授权和共识不同：** “某人可以修改记录”不等于“所有成员同意该方案”。需要争议处理的决定应标记为待讨论，而不是因为有操作权限就被包装成全体共识。

## 4. 产品信息架构与术语

### 4.1 一级导航

1. **Rooms：** 各项目或创意空间的入口。
2. **Inbox：** 对当前成员有意义的 @提及、待确认变更、重要阻塞与反馈。
3. **Search：** 跨授权 Room 搜索消息、会议、决定、实验、Demo 和关联代码。
4. **Settings：** 工作空间、权限、存储、AI、集成和数据导出。

### 4.2 Room 内的工作区

| 区域 | 核心内容 | 主要交互 |
| --- | --- | --- |
| Overview | 当前目标、有效决策、活跃实验、下一步、变化摘要 | 快速恢复 |
| Discussion | 群聊、话题线程、引用、文件、@AI | 自由交流 |
| Meetings | 发起会议、屏幕共享、纪要、转录与时间点 | 实时讨论与沉淀 |
| Explore | 假设、实验分支、Demo、反馈和结论 | 快速验证方向 |
| Plan | 阶段目标、任务、依赖、阻塞和修订原因 | 人类动态规划 |
| Context | 决策、关系、知识来源、修订历史 | 查询当前有效事实 |
| Review | 候选变更、批量确认与审核记录 | 低摩擦沉淀 |

移动端早期以阅读、讨论、会议参与和反馈为主；复杂审核和开发工具操作优先适配桌面 Web。

### 4.3 核心概念

- **Room：** 持续存在的协作边界，成员、权限、讨论与项目上下文的容器。可关联一个或多个代码仓库，但不强制有仓库。
- **Source Event：** 来自消息、会议、演示、反馈或代码系统的原始事件及其出处。
- **Decision：** 经过有权限成员确认、具有生命周期的正式结论。
- **Experiment：** 为回答具体假设而开展的探索，允许同一目标有多个竞争方案。
- **Artifact／Preview：** 可验证的输出，如 Demo、构建、截图、录屏或报告，具有版本与访问范围。
- **Work Item：** 执行层面的任务、问题或阻塞，可选关联实验、计划与 Agent 结果。
- **Plan：** 当前目标、优先级、任务与依赖的版本化工作视图。
- **Context Link：** 有类型和证据来源的对象关系。
- **Change Proposal：** AI 或成员提出、尚未正式生效的结构化变更。
- **Context Revision：** 一次经确认的共享上下文修订。
- **Context Packet：** 面向成员或 Agent 的按权限、范围和版本生成的上下文包。

## 5. 关键用户旅程

### 5.1 旅程 J1 从想法到两个 Demo

1. 发起人在 Room 内抛出一个不成熟的想法，成员自由讨论。
2. 大家明确当前需要验证的问题，例如“多人同时决策是否有趣”。
3. AI 从讨论中提出一项假设、两个实验方向与待确认行动项。
4. 成员在 Review 中编辑并确认实验，不要求把所有闲聊结构化。
5. 两位开发者分别使用自己的 Agent，通过 CLI 获取目标、约束和已确认决定。
6. 开发者发布两个可体验 Demo，关联实验与代码版本。
7. 其他成员打开 Demo、留下反馈；反馈固定关联到对应 Demo 版本。
8. 团队比较体验，确认保留一个方向；Plan 与 Decision 产生可追溯修订。

**完成标准：** 不依赖外部 IM；不同 Agent 的开发者无需手动复制长篇聊天记录；团队能指出决定的原始依据与 Demo 反馈。

### 5.2 旅程 J2 会议结束后沉淀结论

1. 成员在 Room 内发起语音会议，按需要共享屏幕；录制与转录需要明确告知和同意。
2. 会议期间可标记时间点或引用正在讨论的实验。
3. 会议结束后，系统生成可编辑摘要和候选决策、行动项、开放问题。
4. 审核者检查候选变更的来源片段与影响范围。
5. 审核者采纳、编辑、稍后处理或忽略；普通项目记录可批量确认，重大方向变更单独确认。
6. 确认后，Room 的当前视图与 Agent Context Packet 更新；未确认内容保持候选身份。

### 5.3 旅程 J3 @AI 协助突破僵局

1. 团队讨论两个方案都不理想。
2. 成员在当前线程 @AI，提出具体问题。
3. AI 在授权范围内获取本线程、当前决策、已有实验与反馈，给出分析、方案与证据引用。
4. AI 的回答是讨论消息，不会直接变成 Decision 或修改 Plan。
5. 团队认可建议后，可以显式保存为候选变更，或继续由后台提取等待审核。

### 5.4 旅程 J4 缺席成员与 Agent 恢复

1. 成员进入 Room Overview，查看“自上次访问以来变化”。
2. 视图优先显示已确认的决定、实验状态、关键反馈、阻塞及仍未确认的重要提议。
3. 成员点击一项决定即可回到原始讨论或会议时间点。
4. Coding Agent 使用 Room／Experiment 标识读取 Context Packet，其中包含版本号、有效决策、任务范围与来源引用。
5. 如果 Context Packet 已过期，客户端可以获取增量变化并提示成员重新检查有影响的工作。

### 5.5 旅程 J5 决策被推翻

1. 原 Decision A 为“使用技术方案 X”。
2. 新讨论提出方案 Y；AI 识别出可能冲突，但不直接宣布 Y 生效。
3. Review 展示“拟替代 Decision A”，附新旧内容、原始证据与影响对象。
4. 有权限成员确认后建立 Decision B 和 supersedes 关系。
5. 普通搜索以 B 为当前有效决定，同时仍能查到 A 的历史原因。
6. Agent 读取当前上下文不再把 A 当作有效约束；需要查根因时可沿来源继续展开。

## 6. 功能需求

### 6.1 FR-01 Room 与成员管理

**优先级：P0**

- FR-01.1 创建、重命名、归档 Room；Room 拥有稳定标识、描述、成员与时区。
- FR-01.2 邀请成员、移除成员、设置 Owner／Member／Guest 权限。
- FR-01.3 可选关联多个仓库或已有项目链接；不要求使用指定 Git 服务。
- FR-01.4 Room 首页展示目标、活跃实验、最近确认变化、待审核数量和下一步。
- FR-01.5 默认仅 Room 成员可浏览记录；跨 Room 共享须显式授权。
- FR-01.6 删除或导出前显示影响范围，并保留合理的恢复策略。

**验收：** 新团队无需配置外部聊天账号即可创建 Room、邀请成员并进行第一次讨论；Guest 无法读取未授权的私有内容。

### 6.2 FR-02 群聊与讨论

**优先级：P0**

- FR-02.1 支持多人实时文本消息、基本 Markdown、代码块、文件附件、表情反应和 @提及。
- FR-02.2 支持回复线程、稳定消息链接、编辑与删除记录；引用失效时展示明确状态。
- FR-02.3 支持直接引用 Decision、Experiment、Work Item、Demo 与会议时间点。
- FR-02.4 支持消息搜索、未读定位、按话题查看以及与实验或任务关联。
- FR-02.5 @AI 在当前线程按需回答；不会未经邀请持续发送建议。
- FR-02.6 被删除或撤权的内容不得继续通过搜索、摘要或 Agent API 泄露。

**P1：** 消息固定、话题分组、草稿同步、消息级原位候选预览。**P2：** 完整移动推送、高级富媒体和第三方 IM 导入。

**验收：** 成员可以在聊天中提及一个实验，另一成员能从该链接直达实验版本；@AI 回答附授权范围内的有效来源。

### 6.3 FR-03 内建会议与纪要

**优先级：P0 基础会议；P1 完整自动转录体验**

- FR-03.1 Room 内发起或加入语音会议；MVP 面向少量成员设计，具有可见的参与者和麦克风状态。
- FR-03.2 MVP 支持屏幕共享和基础会议内文字记录；摄像头、多流布局和设备切换优化列为 P1。
- FR-03.3 会议拥有稳定 ID、标题、参与者、起止时间与关联 Room。
- FR-03.4 会议纪要可人工编辑；具备转录能力时，按时间点关联原始转录证据。
- FR-03.5 录音、录屏与转录遵守显式同意、可见状态、可配置保留期与访问控制。
- FR-03.6 会议结束后可主动触发整理；可用的 AI 输入自动生成候选决策、行动项和开放问题，进入 Review。
- FR-03.7 AI 不把不确定的说话人识别或模糊承诺自动转成已确认任务。

**降级要求：** 若 STT 尚不可用或服务失败，会议仍可正常开展，成员仍能手动记录与确认纪要；音视频能力不应依赖外部协作产品账号。

**验收：** 一次会议结束后，成员能形成可追溯的纪要和审核候选；没有同意录制的会议不会被后台悄悄录音。

### 6.4 FR-04 共享上下文与检索

**优先级：P0**

- FR-04.1 原始事件有稳定 ID、类型、作者或系统主体、时间、来源和权限范围。
- FR-04.2 保留当前有效决策、历史决策、实验结论、任务状态与计划修订。
- FR-04.3 检索支持关键词、对象类型、Room、时间、状态与来源筛选。
- FR-04.4 查询结果区分“已确认”“候选”“历史失效”“AI 推断”；不得混用。
- FR-04.5 Context Link 至少具有关系类型、来源目标、建立者、证据、确认状态与失效状态。
- FR-04.6 支持通过对象关系回溯消息、会议时间点、代码引用及具体 Demo 版本。
- FR-04.7 每个正式对象提供变更历史，并显示最新更新时间及确认人。

**P1：** 语义检索、相关路径逐步召回、跨多个 Room 的授权聚合。**P2：** 专用知识图谱引擎。

### 6.5 FR-05 Context Review 变更审核

**优先级：P0，产品核心**

- FR-05.1 AI 可从群聊、会议、Demo 反馈与受信任集成事件中提取六类候选：Decision、Experiment、Work Item、Plan Change、Open Question、Evidence Link。
- FR-05.2 候选结构包含操作类型、目标对象、建议内容、来源引用、证据片段、影响范围、基础版本与状态。
- FR-05.3 AI 在形成审核批次前执行重要性过滤、语义去重、相对当前正式状态的增量比较和话题聚合。
- FR-05.4 以会议结束、讨论收束、反馈积累或用户主动请求等自然时机形成审核批次；不按每条消息弹窗。
- FR-05.5 对候选提供采纳、编辑后采纳、稍后处理、忽略和查看来源操作。
- FR-05.6 允许多条普通变更一次提交；替代正式决策、改变项目总体方向或授权范围的变更必须单独明确确认。
- FR-05.7 提交前展示“修改前 → 修改后”、受影响对象、冲突与有无未解决责任人。
- FR-05.8 审核使用版本前提条件；基础版本失效时重新检查冲突并阻止静默覆盖。
- FR-05.9 确认写入新 Context Revision，记录审核者、时间、变更集合与证据。
- FR-05.10 未确认候选不得混入 Current Decisions；如果在 Agent 包中出现，必须明确标记为 pending。
- FR-05.11 支持重复候选合并、撤回错误候选、重开已暂缓项和确认后的修订；不可无痕篡改审计历史。
- FR-05.12 AI 故障时，成员仍可手动创建 Decision、Experiment 与任务。

**验收：** 一场会议产生的多条有价值变化可集中审核；采纳后更新相关正式状态；忽略候选不会变成团队共识；冲突决策不能被自动替代。

### 6.6 FR-06 Decision 与当前共识

**优先级：P0**

- FR-06.1 Decision 至少包含标题、结论、适用范围、状态、确认人、确认时间、来源证据和修订版本。
- FR-06.2 状态包含 proposed、active、superseded、revoked；被替代必须指向新的决定或说明撤销原因。
- FR-06.3 可由讨论、会议或实验结论创建；人工确认后方可 active。
- FR-06.4 同一个主题允许保留历史决定；默认查询当前有效版本，历史记录可明确展开。
- FR-06.5 决策影响已有任务和实验时，标记“需检查”，不得未经授权直接取消任务。

### 6.7 FR-07 Experiment 与快速验证

**优先级：P0**

- FR-07.1 可从讨论或 Review 创建实验；不要求预先生成 Jira 式任务清单。
- FR-07.2 实验记录假设、要回答的问题、判断标准、负责人、状态、候选方案、相关 Artifact 和反馈。
- FR-07.3 同一目标允许并行多个实验；实验之间可以比较，而不是强制串行。
- FR-07.4 状态包含 draft、active、evaluating、concluded、stopped；结论支持“支持假设”“不支持”“证据不足”。
- FR-07.5 结束实验不删除失败证据；可标注停止原因与再启动条件。
- FR-07.6 实验反馈可以转成候选决定、开放问题或任务，但未经确认不改变正式计划。

**验收：** 一个 Room 可以创建两个并行实验，分别挂载 Demo，收集体验反馈并形成可追溯的方向选择。

### 6.8 FR-08 Demo、Artifact 与体验反馈

**优先级：P0 最小 Web Demo 分享；P1 本地实时 Preview 网关增强**

- FR-08.1 Artifact 拥有稳定 ID、类型、版本、创建人、所属实验、时间、可见范围与来源说明。
- FR-08.2 MVP 支持登记现有 Web URL 或上传可访问的静态 Demo；无需推动整个团队先合并代码。
- FR-08.3 提供低操作成本的本地 Web Preview 分享路径：受控的开发者 CLI 建立短期会话，生成可撤销的访问链接；在技术可行性验证完成前不作为无条件的跨网络可达承诺。
- FR-08.4 Preview 链接必须绑定某个明确运行实例或版本，展示创建时间、会话状态、失效时间与来源信息。
- FR-08.5 访客对具体 Artifact 版本发表评论；新版 Demo 发布后，旧版反馈仍引用旧版本，不被自动迁移。
- FR-08.6 支持反馈转为候选问题、实验结论与任务；可引用截图或具体页面位置（P1）。
- FR-08.7 本地 Preview 只暴露指定端口与资源；不得演变为任意命令执行代理或读取宿主其他文件。
- FR-08.8 访问权可按 Room 成员、单次邀请和到期时间限制；支持手动结束会话。

**P1：** 运行中 Demo 版本快照、屏幕批注、自动附加 Git SHA 与工作区脏状态。**P2：** 非 Web App 的可交互远程执行与通用桌面应用流化。

**验收：** 成员可以在不读取开发者本地代码的情况下访问授权 Demo，并对确切版本反馈；链接撤销后不再可用。

### 6.9 FR-09 Plan 与 Work Item

**优先级：P0 轻量计划；P1 依赖与智能冲突检测**

- FR-09.1 Plan 展示目标、阶段、实验优先级、待办、阻塞、负责人和最近修订。
- FR-09.2 Work Item 可独立创建或关联 Experiment／Decision；并非所有讨论都必须创建任务。
- FR-09.3 AI 可以推荐合并重复工作、调整优先级和识别依赖，但不得直接更改正式分工或取消任务。
- FR-09.4 计划修订要保留旧状态、变更原因、确认人和关联证据。
- FR-09.5 面对并行探索，明确区分“假设尚未验证”和“正式承诺交付”。
- FR-09.6 任务被分配给某人之前，应有可核实的接受状态；AI 不能根据模糊话语自动认定承诺。

### 6.10 FR-10 AI 参与讨论与助手

**优先级：P0 基础 @AI，P1 跨对象推理增强**

- FR-10.1 只有被 @或主动调用时才在聊天线程发言；后台发现的普通建议汇入 Review／Overview，不持续群发。
- FR-10.2 回答默认基于当前线程、有效 Decision、相关 Experiment、Artifact 反馈与用户权限范围。
- FR-10.3 输出可区分引用事实、推断、建议和不确定信息，提供可点击来源。
- FR-10.4 能协助头脑风暴、提出实验方案、比较方案、发现计划冲突、总结下一步，但不能自动确认正式决定。
- FR-10.5 模型不可用时，讨论、会议、人工决策和检索应能降级使用。
- FR-10.6 面向会议和聊天的 AI 处理需提供可见的启用配置与数据传输边界。

### 6.11 FR-11 外部 Agent 接口

**优先级：P0 CLI／HTTP API；P1 MCP 适配与增量订阅**

- FR-11.1 CLI 与 HTTP API 返回稳定 JSON 数据结构、错误码和版本信息。
- FR-11.2 按 Room／Experiment／Work Item 读取 Context Packet，不要求客户端理解内部表结构。
- FR-11.3 包含当前有效决策、任务范围、实验假设、最近变化、待解决问题、相关代码／Demo 引用和数据时间戳。
- FR-11.4 支持有限的成果回传：进展说明、提交引用、Artifact 链接、测试结果；回传内容有来源身份与人工可核验状态。
- FR-11.5 凭据具有最小权限；本地目录、私有 Session、未提交代码默认不上传。
- FR-11.6 返回 context_revision；客户端可查询自某版本以来的变化，并检测过期上下文。
- FR-11.7 Agent 的输出不自动升级为 Decision；需经过成员明确确认。
- FR-11.8 不代替开发者运行 Agent，不执行代码修改、合并、发版等高风险操作。

**P1：** 提供 MCP tools/resources 映射、有限的事件订阅。**P2：** 可选外部编排系统适配器，不进入 Demble 核心运行时。

### 6.12 FR-12 Inbox、通知与变化摘要

**优先级：P0 Review 待办计数与 @提及；P1 个人化通知**

- FR-12.1 Inbox 汇总待审核批次、@提及、直接分配、重要阻塞和 Demo 反馈。
- FR-12.2 提供“自上次访问以来”的增量摘要，避免重新阅读所有聊天消息。
- FR-12.3 对相同主题去重和聚合；默认不把每个 AI 提取动作发送通知。
- FR-12.4 待确认项可稍后处理、合并或忽略；原始证据仍可查。
- FR-12.5 提醒只在有合理行动价值时触发；用户可配置静默时间和关注范围（P1）。

## 7. Context Review 详细交互与规则

### 7.1 候选的产生时机

| 触发点 | 默认处理 | 打扰级别 |
| --- | --- | --- |
| 聊天持续进行 | 异步索引、聚合潜在变化，不逐条弹窗 | 静默 |
| 有人点击“整理本次讨论” | 生成当前线程的 Review Batch | 用户主动 |
| 会议结束 | 在可用输入基础上生成纪要与候选 | 会议页面提示 |
| Demo 收集一批反馈 | 合并重复反馈，提议问题或实验结论 | Explore 页面提示 |
| 重要决策冲突被检测到 | 标为“可能冲突”，等待核查 | Room 内轻量提醒 |
| 用户再次打开 Room | 展示与其有关的待办和确认变化 | 摘要，不强迫处理 |

不能把“模型对某句话有很高置信度”作为自动生效条件。置信度只影响候选排序与是否需要人工复核，不等同于授权或共识。

### 7.2 候选变更卡片

每张卡片固定呈现：

1. **建议操作：** 新增、更新、替代、撤销、关联或标记待检查。
2. **建议内容：** 简洁的人类可读陈述；避免长篇模型解释。
3. **前后差异：** 如果修改已有对象，明确展示 before／after。
4. **证据：** 消息永久链接、会议时间戳、Demo 版本、Commit 等。
5. **影响范围：** 可能改变的 Decision、Experiment、Plan、Work Item 或 Agent Context。
6. **可信状态：** 确认事实、AI 推断、存在歧义或与现有状态冲突。
7. **审核操作：** 采纳、编辑后采纳、稍后、忽略；具有权限时提交。

MVP 中来源必须可点击回到原始对象；当来源被删除、权限撤销或内容不可用时，卡片应显示“证据不可查看”，并降低确认便利性，不能呈现为仍可完整核实。

### 7.3 批量审核策略

- 同一会议或同一话题生成一个主要批次，重复候选合并为一条并保留多处证据。
- 默认仅把用户明确选择的候选纳入提交；不提供暗含复杂影响的“全部自动通过”。
- 系统在提交前验证目标对象版本、权限和冲突。无冲突的多条变更可在一次事务中落地；冲突项单独返回检查。
- 如果一个批次包含重大决策替代，需单独展开前后对比并二次明确确认。
- “稍后”不会成为正式状态；有新增证据时可以重新浮现，不能无限重复打扰。
- “忽略”只表示该候选不应再反复出现，不删除原始事件；新事实变化可以产生新的候选。
- 编辑候选需保留 AI 原建议与人工修改差异，最终以人工确认文本为准。

### 7.4 状态机

**Change Proposal：** extracted → grouped → pending_review → accepted／edited_and_accepted／deferred／dismissed／superseded。只有 accepted 或 edited_and_accepted 会触发正式 Context Revision。

**Decision：** proposed → active → superseded／revoked。历史状态不可通过物理覆盖抹去；撤销、替代和修订均需记录原因。

**Context Revision：** 每个 Room 的正式上下文版本单调递增，产生时间、提交者、基本版本、变更对象列表与来源引用。并发审核须使用乐观并发控制或等价机制，拒绝覆盖更新。

### 7.5 不确定性与冲突处理

- AI 不确定消息属于哪个实验时，候选进入未归属集合，显示可能匹配对象与证据，由成员选择；不得强制归档。
- 发言是建议、玩笑或反对意见时，不应默认识别为正式承诺。
- 会议摘要声称“全体同意”，但原始转录未能证明时，不允许将其作为无人核实的事实。
- 新旧决定冲突时，明确标记“讨论中”或“待替代确认”，不可依赖时间较晚就直接覆盖。
- 多成员同时审核时，已失效候选需刷新并重新确认。
- 不能访问证据的 Guest 或 Agent 不应通过候选摘要间接获取超出授权的信息。

### 7.6 审核后的用户反馈

提交后展示：已更新的对象、正式版本、尚待处理的冲突、可撤销／修订入口。关联成员只接收与其行动有关的精简变化摘要；不要求所有成员重新阅读整个会议纪要。

## 8. 关键界面与交互规范

### 8.1 Room Overview

默认首屏回答“我们在做什么、最近什么变了、接下来做什么”。建议布局：

- 顶部：Room 名称、目标、成员、会议入口、创建实验按钮。
- 主区：当前有效决策（少量）、活跃实验与 Demo、下一个重要行动。
- 侧区：自上次访问的正式变化、需要本人处理的审核和 @提及。
- 深入入口：完整讨论历史、Context 关系、旧决策和归档实验。

如果 Room 还没有正式决定，显示“尚未确认的共识”，而不是让 AI 虚构一份项目目标。

### 8.2 Discussion

聊天为默认低门槛入口；成员可自然发送消息。消息的“转为实验／决策候选”“引用到任务”“提及 AI”是邻近操作，而不是强迫每句话都选择对象类型。长讨论可以按线程折叠；AI 的后台发现以非侵入标记呈现。

### 8.3 Review Inbox

按 Room、来源批次、变更类型和风险显示候选。列表只展示变更摘要；点击展开差异、原始证据及影响范围。桌面端支持多选批量提交、键盘快速审核与修改草稿；移动端先保证单条审核可用。审核者不需要阅读整段转录才能确认每个候选，但始终能够回看。

### 8.4 Explore

以“正在验证的问题”为一级标题，展示多个并行方向。每个 Experiment 卡片有假设、负责人、状态、Demo、最近反馈与结论。比较视图优先展示体验证据和判断标准，而非只比较代码完成度。

### 8.5 Demo Feedback

访问者始终看到自己正在体验的版本标识和更新时间。反馈输入靠近 Demo，支持文本和基础评分／观察类型（例如有效、困惑、缺陷）；反馈提交后固定关联版本。实验负责人可以批量查看、归类并转成候选问题。

### 8.6 Plan

默认精简的阶段目标与任务列表，不强制 Scrum 流程。变更视图显示“此前 → 当前”和原因；对 AI 提出的重排或冲突建议提供审核入口，而非悄然改动卡片位置。

## 9. 逻辑数据模型

### 9.1 核心实体

| 实体 | 关键字段 | 核心约束 |
| --- | --- | --- |
| Workspace | id、name、settings | 数据与成员管理边界 |
| Room | id、workspace_id、goal、context_revision | 稳定协作边界 |
| Membership | subject_id、room_id、role、grants | 所有读取与写入经过授权 |
| SourceEvent | id、room_id、type、author、occurred_at、payload_ref、visibility | 原始证据与删除策略 |
| DiscussionThread | id、room_id、root_event_id | 聊天上下文和回复关系 |
| Meeting | id、room_id、started_at、ended_at、consent_state | 记录会话及转录范围 |
| Decision | id、room_id、text、status、version、approved_by | 正式结论的生命周期 |
| Experiment | id、room_id、hypothesis、criteria、status、owner | 验证问题而非默认交付任务 |
| WorkItem | id、room_id、scope、status、assignee、accepted_at | 轻量任务及责任状态 |
| PlanRevision | id、room_id、before_ref、after_ref、approved_by | 计划可回溯 |
| Artifact | id、experiment_id、kind、version、source_ref、access_policy | Demo 与反馈的稳定目标 |
| Feedback | id、artifact_id、author、body、created_at | 不跨 Demo 版本误绑定 |
| ContextLink | source、target、relation、evidence、status、created_by | 类型化证据关联 |
| ChangeProposal | id、operation、target、base_version、proposal、evidence、status | 未确认的结构化变化 |
| ReviewBatch | id、room_id、proposal_ids、reviewer、status | 组织审查但不等于生效 |
| ContextRevision | id、room_id、base_revision、changes、actor、timestamp | 正式状态变更日志 |
| AgentCredential | id、subject、scopes、expires_at、revoked_at | 最小权限与审计 |

逻辑模型不要求一张表对应一个实体。初期可采用关系数据库与对象存储；可检索文本、文件及媒体索引在权限与保留策略下构建。所有对象使用不可复用的稳定 ID，避免引用因重命名或位置移动失效。

### 9.2 Context Link 关系集合

首版建议仅开放有明确语义的有限关系：discusses、proposes、decided_in、supersedes、implements、demonstrates、verified_by、feedback_on、blocks、relates_to。

关系有两种不同可信状态：explicit／confirmed（用户显式建立或确认）和 inferred（AI 推断）。例如，“Commit 修改了相关文件”并不自动证明“Commit 实现了某项 Decision”；implements 应有人的确认或可信工作流证据。

### 9.3 分领域事实来源

| 领域 | 权威来源 | Demble 维护的内容 |
| --- | --- | --- |
| 聊天与会议 | 原始消息、音视频／转录记录 | 索引、引用、纪要与提取候选 |
| 代码历史 | Git 仓库与 Commit | 代码引用及其与实验的关系 |
| 团队正式决定 | 已确认的 Decision 修订 | 当前有效视图、替代关系与证据 |
| Agent 私有执行 | 各自 Harness／本地环境 | 经用户授权回传的结果与 Session 引用 |
| Demo 体验 | 对应 Artifact 的具体版本 | 访问、反馈、版本与来源关系 |

不应把 AI 摘要设计为覆盖所有领域的唯一事实来源。

### 9.4 删除、修正与可追溯性

对原始事件的删除或权限撤销要传播至索引、缓存和衍生检索结果；对于已依据该事件形成的决策，保留“曾有引用但来源已不可见”的审计事实，同时限制敏感原文继续传播。正式决策可通过修订或撤销纠错，而不是悄悄修改旧版本。备份与保留期遵循 Room 配置和法律／团队约定，不能承诺一切数据永不删除。

## 10. Agent 接口契约

### 10.1 设计原则

CLI、HTTP API、未来 MCP 适配器共用一套鉴权与领域语义。客户端不应依赖网页 DOM、特定模型提示词或内部数据库字段。所有响应包含稳定 ID、权限过滤结果、数据版本、更新时间及明确错误。

### 10.2 建议命令

以下是需求层面的示例，不表示这些命令已实现：

~~~bash
room auth login
room room list --json
room context pack --room game --experiment EXP-B --json
room context changes --room game --after-revision 27 --json
room decision list --room game --status active --json
room experiment show EXP-B --json
room artifact publish --experiment EXP-B --url https://demo.example.test --json
room progress report --work-item TASK-34 --commit a1b2c3 --json
room preview share --room game --experiment EXP-B --port 3000
~~~

### 10.3 Context Packet 样例

~~~json
{
  "schema_version": "0.1",
  "room_id": "game",
  "context_revision": 28,
  "generated_at": "2026-11-02T10:00:00+08:00",
  "scope": {"experiment_id": "EXP-B"},
  "goal": "验证多人实时互动是否有趣",
  "current_decisions": [
    {"id": "DEC-19", "version": 1, "text": "优先验证多人互动",
     "evidence_refs": ["meeting:8@24:18"]}
  ],
  "superseded_decisions": [{"id": "DEC-12", "superseded_by": "DEC-19"}],
  "work_items": [{"id": "TASK-34", "status": "needs_review"}],
  "open_questions": [{"id": "Q-8", "text": "同步机制如何简化"}],
  "artifacts": [{"id": "ART-7", "version": 2, "experiment_id": "EXP-B"}],
  "pending_change_count": 2,
  "source_links": {"DEC-19": ["meeting:8@24:18"]}
}
~~~

正式上下文和未确认提案必须以不同字段或调用结果表达。默认上下文包不把 pending 内容当作可执行要求。调用方可显式请求待讨论信息用于分析，并显示其状态。

### 10.4 写入与执行边界

Agent 或 CLI 可以在授权范围内上报 Artifact、进展、测试证据和待审核提案。提交正式 Decision、修改团队 Plan、设置新的任务责任人等操作必须校验对应用户的权限与确认流程。若未来引入 Worker 执行系统，授权 Mandate 必须独立于 Decision，且由服务端与执行工具实施。

### 10.5 同步与一致性

每个读取响应返回当前 context_revision。Agent 在执行前可记录基础版本，在报告成果时附带该版本；若重要决定在其运行期间变更，Room 应显示“可能基于过期上下文”，并提供 changes 增量。系统不试图远程篡改外部 Agent 当前 Session。

## 11. 非功能需求

### 11.1 部署与可维护性

- **NFR-01 自托管：** 提供明确安装、升级、备份与恢复路径；日常使用无需第三方协作平台账号。
- **NFR-02 可配置 AI：** AI 模型服务通过适配器配置，提供不开启 AI 时的基础手工工作流；模型不可用不应阻断聊天与会议。
- **NFR-03 开放接口与互操作：** 核心协议与数据导出格式有文档；避免以单一 Harness SDK 作为领域模型。
- **NFR-04 可迁移数据：** 支持按 Room 导出标准结构化记录、附件索引和引用关系；导出需权限校验。
- **NFR-05 小团队优先：** 首个部署目标是 2–10 名成员，不为了假想的万人规模引入过度分布式架构。

### 11.2 建议的初期体验预算

以下为设计目标，需通过原型测试校准，非已实现承诺：

| 指标 | MVP 目标 |
| --- | --- |
| 实时消息体感 | 在常见家庭／校园网络下稳定、低延迟；测量发送到可见时间 |
| Room Overview | 常规数据量下首屏主要信息在 2 秒左右可交互 |
| 关键词检索 | 常规 Room 的典型查询在 2 秒左右返回首批结果 |
| Context Packet | 常规范围读取在 3 秒左右返回，不含外部模型生成时延 |
| Review 批次 | AI 处理异步进行，用户可离开；有进度、失败重试和人工兜底 |
| Demo 分享 | 已启动的受控分享会话应在短操作路径内获得链接 |

这些数值将基于设备、网络、Room 数据量与自托管资源设定正式 SLO；不把 AI 响应速度与确定性 API 的延迟混为一谈。

### 11.3 可靠性、审计与恢复

- 审核提交采用原子更新或明确的部分失败补偿策略；不能出现“界面显示成功但正式上下文只更新一半”。
- 消息发送、AI 提取、Agent 进展上报与反馈接收须考虑重试、幂等和去重。
- 重要状态变更有审计日志，至少记录主体、对象、操作、前后版本与时间。
- 支持日常备份与恢复演练；原始媒体大文件与结构化数据库的恢复一致性要测试。
- 会议媒体故障与 AI 服务故障不得导致已保存聊天或正式决策丢失。

### 11.4 安全与隐私

- 强制鉴权、Room 级授权和对象访问检查；搜索、预览、Context Packet、来源回溯与 AI 检索都使用同一权限边界。
- 服务端密钥和 Agent 令牌不进入聊天文本或公开 Demo；令牌可限定作用域、到期与撤销。
- 共享 Demo 使用临时、可撤销授权，不直接暴露开发者文件系统或本地管理接口。
- 对聊天、会议、附件及代码片段的 AI 处理提供数据流向说明和配置；默认不将私有本地代码自动上传。
- 记录／转录时参与者可见状态与同意管理；没有权限的转录不会进入搜索或 AI 上下文。
- 防御来自聊天、文档、网页和 Demo 反馈的提示注入：把这些内容视为数据，不允许它们改变服务端权限或 Agent 写入范围。
- 审核、AI 输出、导出和删改操作留下适当的审计信息，同时避免审计系统泄露敏感原文。

### 11.5 可访问性与国际化

桌面 Web 需支持键盘操作、焦点可见、基础屏幕阅读语义和明确状态文本；关键状态不能只用颜色区分。首版以中文为主，数据模型、日期和 UI 文案预留国际化能力。

## 12. MVP 计划与阶段性交付

### 12.1 切片 S0 可用的团队空间

**目标：** 三位成员能独立使用 Room 沟通与进行一次会议。

范围：身份／邀请、Room、实时群聊、引用链接、基础语音和屏幕共享、会议记录与基础权限。AI 暂时可以不接入。完成门槛：不需要外部 IM 账号；消息和会议对象有稳定 ID；权限隔离通过基础测试。

### 12.2 切片 S1 共享上下文闭环

**目标：** 从讨论和会议得到可信、可追溯的正式决定。

范围：Decision、Source Event、Context Link、手工创建对象、AI 候选提取、Review Inbox、批量审核、Context Revision、当前状态检索。完成门槛：同一会议能经人工确认形成决定；旧决定被替代后不会作为最新决定返回；来源可点击核查。

### 12.3 切片 S2 实验到 Demo

**目标：** 一个想法能在 Room 中形成两个可比较的实验。

范围：Experiment、轻量 Plan、Artifact、Web URL／静态 Demo、版本反馈、实验比较；优先验证受控本地 Preview 方案的可用性与安全边界。完成门槛：两个不同开发者提交可体验成果；反馈不串版本；实验结论能通过 Review 更新计划。

### 12.4 切片 S3 Harness-agnostic 协作

**目标：** 两种不同 Coding Agent 可获得同一份最新且有来源的团队上下文。

范围：CLI／HTTP API、Context Packet、context_revision、权限令牌、有限的进度／成果回传、过期上下文提示。完成门槛：不同客户端按相同语义读到有效 Decision；未确认候选不冒充正式要求；成果回流至对应实验。

### 12.5 切片 S4 日常使用优化

**目标：** 降低长期使用中的消息、审核与恢复负担。

范围：增量摘要、去重、讨论收束触发、AI @讨论增强、搜索改善、转录优化、性能与错误恢复。完成门槛：连续使用两周的真实团队能够量化信息恢复时间和审核成本，并根据数据决定后续范围。

### 12.6 分期优先级总览

| 能力 | MVP 基础 | 首次增强 | 暂缓 |
| --- | --- | --- | --- |
| 内建群聊 | 实时文本、线程、引用、附件 | 高级通知、消息整理 | 社交化功能 |
| 会议 | 语音、共享、手工纪要、AI 可选整理 | 自动转录、时间点回放、视频优化 | 大规模会议平台 |
| Context Review | 候选、去重、批量审核、修订 | 更细粒度冲突检测 | 自动决定方向 |
| 实验 | 假设、多方案、结论、反馈 | 实验模板与体验对比 | 全自动研究调度 |
| Demo | URL／静态制品、版本反馈 | 受控本地动态 Preview 完善 | 通用远程桌面 |
| Agent | CLI／API 上下文与成果回传 | MCP、订阅 | 托管 Worker 集群 |
| 计划 | 人类维护、可审计修订 | AI 依赖与冲突建议 | 自治计划执行 |

阶段按验证依赖排序，不承诺未经估算的固定开发工期。基础会议与动态 Preview 是高风险技术点，允许在原型阶段使用成熟开源基础组件与简化功能，但不应从产品目标中删除。

## 13. 成功指标与产品验证

### 13.1 北极星与核心指标

**北极星目标：** 降低小团队把想法转化为可体验、可比较且具有共同理解的成果所需的协调成本。

| 指标 | 定义 | 如何采集 |
| --- | --- | --- |
| Idea-to-Demo Time | 从创建实验／明确想法到首个可体验版本的时间 | 实验与 Artifact 时间戳 |
| Context Recovery Cost | 缺席成员或新 Agent 恢复正确状态的人工解释次数与耗时 | 任务观察、访谈、操作日志 |
| Coordination Overhead | 用于寻找资料、同步状态、搬运上下文和确认分工的额外操作 | 观察记录与用户反馈 |
| Review Time | 每个审核批次的有效处理时间 | Review 交互事件 |
| Candidate Acceptance Rate | 候选被采纳的比例，分类型观察 | Proposal 状态 |
| Material Correction Rate | 候选在事实、责任人或状态上需重大修改的比例 | 审核前后差异 |
| Context Correctness | 被询问的当前有效决策及其证据是否准确 | 人工抽样与场景测试 |
| Demo Feedback Loop | 每个实验获得反馈、形成结论并更新计划的周期 | 实验、反馈与修订时间 |

不能只追求提取更多候选或提高采纳率。模型可能通过少提建议提高采纳率，因此需结合漏提、错误归档、人工修正与信息恢复正确率综合判断。

### 13.2 试点计划

邀请最初目标中的 3–5 名同学，以一个真实、方向未定的小项目连续使用至少两周。试点前记录现有工具下从讨论到 Demo、从缺席到恢复、从会议到共享结论的基线；试点中记录失败案例、误总结、重复候选、无法访问的 Demo 与权限困扰。以真实操作成本和完成成果质量决定继续开发的优先级。

### 13.3 必须验证的假设

1. 团队愿意把真实日常讨论放在 Demble，而不仅把它当成存档网站。
2. AI 候选审核比人工总结更省时间，并且不会引入不可接受的错误。
3. 开发者愿意从 CLI 读取上下文并回传成果，即使使用不同 Harness。
4. Demo 版本关联和原位反馈能显著缩短方向决策周期。
5. 自托管会议与聊天的维护负担不会抵消上下文整合带来的收益。

## 14. 验收用例

| ID | 场景 | Given／When／Then 验收要点 |
| --- | --- | --- |
| AT-01 | Room 成员隔离 | Guest 无权限时，不能通过页面、搜索、API 或 AI 得到私有消息与决策 |
| AT-02 | 群聊引用 | 两位成员发送、回复并引用实验；引用能定位稳定对象与具体版本 |
| AT-03 | 会议纪要 | 会议结束后能生成可修改纪要，明确区分原始讨论与正式确认项 |
| AT-04 | 批量审核 | 多条普通候选一次确认后，相关对象一致更新并生成 Context Revision |
| AT-05 | 重大决策 | 一条取代当前架构方案的候选不能在普通批量操作中无提示生效 |
| AT-06 | 并发冲突 | 两名成员基于同一旧版本修改同一 Decision，后提交者收到冲突提示 |
| AT-07 | 错误 AI 提取 | 将一句玩笑识别为任务时，审核者可忽略且不会分配正式责任人 |
| AT-08 | 决策替代 | Decision B 替代 A 后，默认查询返回 B；A 保留历史与 supersedes 链 |
| AT-09 | 实验比较 | 一个目标下有两个活跃实验与各自 Demo；反馈和结论可按版本筛选 |
| AT-10 | Demo 撤销 | 分享链接到期／被撤销后不能再访问；反馈仍保留正确版本关联 |
| AT-11 | Agent 一致性 | 两种 Harness 使用相同接口约定读取当前 context_revision 与有效决定 |
| AT-12 | Agent 过期 | Agent 基于旧版本提交结果时，系统提示可能与最新决定不一致 |
| AT-13 | AI 降级 | AI 服务失效时，手工聊天、开会、创建决策及搜索仍可使用 |
| AT-14 | 来源删除 | 来源被撤权后，搜索和 Context Packet 不应泄露原文，引用状态明确 |
| AT-15 | 录制同意 | 未获得录制许可时，不进行隐藏录音或把会议音频发往模型服务 |
| AT-16 | 用户恢复 | 缺席成员能从 Overview 找到最近正式变化及每条的来源 |
| AT-17 | 错误责任归属 | AI 推断某人负责任务时，未获得本人或有权人的确认前不标记已接受 |
| AT-18 | 恶意提示内容 | 用户消息或 Demo 反馈不能通过提示注入绕过读写权限或自动执行命令 |

## 15. 主要风险与缓解

| 风险 | 影响 | 缓解策略 |
| --- | --- | --- |
| 群聊使用率不足 | 无法积累自然上下文 | 先用真实朋友团队验证每日沟通便利性，降低加入和讨论门槛 |
| 同时造聊天、会议、知识和 Demo 过重 | 上线慢、质量分散 | 分垂直切片，复用成熟媒体／存储基础组件，严格区分 P0/P1 |
| AI 错误归档或虚构共识 | 污染长期上下文 | 候选与正式状态隔离、证据引用、批量人工确认、版本修订 |
| Review 积压 | 审核变成新负担 | 去重、按话题合并、优先级、延期与低风险静默处理 |
| 不同 Agent 上下文不一致 | 重复或过期开发 | Context Revision、增量 API、结果回传基础版本 |
| Demo 隧道暴露本地资源 | 安全事故 | 明确端口范围、限时授权、可撤销、隔离执行与预览权限 |
| 音视频质量受网络影响 | 用户回到外部会议工具 | 先验证 2–10 人典型网络，良好降级和可观测性 |
| 自托管部署困难 | 同学不愿持续使用 | 简化安装、备份、升级与故障诊断，试点覆盖低运维环境 |
| 对 AI 厂商过度绑定 | 长期维护与隐私风险 | 统一模型适配层，人工路径始终可用 |
| 权限与来源删除处理不完整 | 信息泄露或审计失真 | 全链路鉴权、衍生索引撤权传播、审计和恢复测试 |

## 17. 研发启动建议与完成定义

### 17.1 建议的启动顺序

1. 将 Room、Source Event、Decision、Experiment、Change Proposal、Context Revision 的领域语义与权限边界定型。
2. 先实现手工可用的聊天／实验／决策流程，再接入 AI 提取，避免 AI 成为系统唯一操作入口。
3. 以一次讨论形成决策为最小 Context Review 端到端测试，再扩展到会议和 Demo。
4. 用两个不同 Harness 验证同一 Context Packet 的读取语义。
5. 分别独立验证会议媒体和本地 Preview 的安全与网络可用性，然后接入主流程。
6. 通过真实小团队试点决定下一轮开发，而非依据功能清单数量决定成功。

### 17.2 MVP 完成定义

MVP 不以“所有 P2 功能未完成”为缺陷。它完成的标志是：一组真实成员可以在自托管 Room 内讨论和开会，确认带来源的决定，开展两个并行实验，访问 Demo 并回传版本化反馈；至少两种不同 Agent 可读取最新有效上下文；团队能够在变化后恢复正确共识，不需要手动复制大段聊天记录；系统未确认的 AI 提议不会冒充正式决定，权限与来源追溯通过验收测试。

### 17.3 后续版本方向

在 MVP 证明协作价值后，优先考虑高级会议转录、Demo 版本快照与批注、Context Packet 增量订阅、计划冲突建议和跨 Room 关系。Agent 编排系统若有需求，应保持外接运行时边界，Demble 继续作为团队协作与可信上下文层。

## 附录 A 产品需求核对清单

- [ ] 不依赖外部 IM 完成基本群聊与会议。
- [ ] AI 默认静默，成员 @AI 时才主动参与讨论。
- [ ] 决策与任务确认由有权的人完成，不由 AI 悄悄生效。
- [ ] 原始事件、AI 候选、正式知识和当前工作视图严格区分。
- [ ] AI 候选具有来源、影响范围、去重和批量审核机制。
- [ ] 决策可以被修订、替代与撤销，历史仍可查询。
- [ ] 一个想法可以并行验证多个 Experiment。
- [ ] Demo、反馈、代码来源与具体版本可关联。
- [ ] 不同 Harness 通过统一机器接口获得相同语义的上下文。
- [ ] 重要的权限边界在 Web、API、搜索和 AI 检索中一致。
- [ ] 成员缺席后能够按增量快速恢复，不必阅读完整历史。
- [ ] 有真实团队的端到端验收与可衡量的协调成本指标。
