# Demble 产品需求（草案）

版本：v0.5 · 更新日期：2026-11-02

这份文档说明 Demble 想做什么、功能应该怎样工作，以及怎么判断做对了。项目还没有可安装版本；技术栈和部分权限、数据规则也没有确定。

**第一次了解项目，先读第 0–5 节；开始做任务时，再查第 6 节的需求编号。**

- [功能清单](#6-功能需求)：FR 编号、优先级和验收要求。
- [数据和接口](#9-逻辑数据模型)：数据对象、状态、命令和 JSON 示例。
- [开发顺序](#12-mvp-计划与阶段性交付)：S0–S4 分别要验证什么。
- [验收用例](#14-验收用例)和[待定问题](#16-还没决定的问题)：实现前要检查、讨论的事情。

开工前先读[开发准备说明](CONTEXT_BASELINE.md)。字段表和命令只是示例，不是已经决定的数据库设计或 API。旧文档里没有在本版确认的实现细节，也不要直接沿用。

## 0. 我们要做什么？

Demble 面向 2–10 人的小团队。大家可以在自己的项目空间里聊天、开会、记录决定，也可以各做一个 Demo，放在一起体验和比较。

团队成员继续使用自己熟悉的 Codex、Claude Code、OpenCode、DSH 等 AI 编程工具。Demble 向这些工具提供项目背景、已经确认的决定、任务和相关资料，并接收开发结果。成员不必反复复制聊天记录，也不必统一开发工具。

这里把这份项目背景和资料称为**共享上下文**。它有一个关键要求：AI 从讨论中整理出来的建议，必须先由有权限的成员检查、修改和确认，才能写进正式的决定、计划或任务状态。原始记录、待审核建议和已确认内容要分开。

例如，三个朋友讨论一个功能，AI 整理出两个值得试的方案。成员确认后，两位开发者分别做出 Demo，其他人体验并反馈，团队再决定采用哪个方向。下一次继续开发时，编程工具读到的是更新后的决定，也能找到当时的依据。

成员决定方向、权限和验收。AI 平时在后台整理信息，被 @或主动调用时才加入讨论。Demble 不负责运行成员的编程工具，也不接管它们的私有会话。

### 0.1 这份文档管什么？

本文定义需求、角色、数据概念和验收条件，不指定语言、框架、数据库或模型厂商。代码和数据结构需要另做技术设计；还没定的问题在第 16 节列出。

保存记录仍要遵守访问权限、删除和保留期限，不能承诺原文永远不删。进度上报记录与正式任务状态的区别，待 OD-08 确认。

### 0.2 优先级怎么读？

- **P0：** 完整 MVP 必须具备的能力。
- **P1：** 第一轮增强，可以先用简化办法验证。
- **P2：** 后续再评估。
- **Out：** 当前不做，除非重新讨论范围。

P0 不等于全部放进 S0。S0–S4 是第 12 节的开发和验证顺序，每次任务仍要写清本次范围和验收条件。

## 1. 为什么需要它？

### 1.1 小团队现在怎么合作

几个人用不同编辑器和 AI 编程工具做项目，代码和原型可以很快写出来。但项目背景散在群聊、会议纪要、个人笔记和编程会话里，大家还得花时间找资料、解释决定、同步进度。

同时做出几个方案之后，比较也不容易：大家体验的可能不是同一个版本，反馈找不到对应页面，也说不清最后为什么选了某个方向。

### 1.2 具体有哪些麻烦

- 讨论过的决定找不到，或者已经推翻的决定还在被引用。
- 换一个工具、换一个人接手，就要重新解释项目背景。
- 聊天很多，但要快速找到“现在确定了什么”很费劲。
- AI 总结混在聊天里，看不出哪些只是建议、哪些已经确认。
- 做 Demo、分享链接、收集反馈和修改计划分散在不同地方。
- 外部聊天和会议平台有各自的账号、数据和权限，资料不容易连起来。

### 1.3 Demble 想改善什么

把讨论、试做、体验和调整计划放在一处，让重要结论能找到依据，也让成员和编程工具知道现在该按什么做。衡量它有没有价值，要看团队少花了多少时间找资料、解释背景和确认状态。

## 2. 哪些原则不能丢？

### 2.1 产品由三部分组成

成员用项目空间聊天、开会、安排实验和分享 Demo。系统保存原始记录、已经确认的内容和修改历史。外部编程工具通过命令行或 API 读取有权访问的内容，并提交结果；支持 MCP 的客户端以后再接适配器。

### 2.2 开发时遵守的原则

1. 方向、优先级、权限和正式决定由人掌握，AI 不替团队拍板。
2. AI 默认不在群里刷屏；后台整理建议，被邀请时再参与讨论。
3. 当前要求以项目里已确认的记录为准，不以某个人的聊天窗口或编程会话为准。
4. 把要验证的问题和可体验的结果放在前面，不先堆复杂任务看板。
5. 不绑定编程工具或模型厂商，成员可以继续用自己熟悉的工具。
6. 尽量在原来的讨论或反馈位置完成引用、整理和确认，少让人重复录入。
7. 正式结论要记清来源、确认人、时间、状态和修改历史。
8. 默认只分享明确授权的内容，本地文件和私有会话不自动上传。
9. 支持自己部署，日常聊天和会议不要求外部协作平台账号；底层可以复用成熟开源组件。

### 2.3 当前不做什么

- 不做通用聊天平台的全部社交功能，也不要求迁移代码仓库或编辑器。
- 不在核心 MVP 中托管编程工具长期运行、自动改代码、合并或发版。
- 不做自主路由、调度和监控 AI 工具的系统。
- 不把每条消息都变成任务，也不把 AI 的判断当成团队共识。
- 不直接内建完整云 IDE、通用 CI/CD 或可以任意代理网络服务的网关。

## 3. 目标用户、角色与权限

### 3.1 主要用户

| 用户 | 日常目标 | 关键需求 |
| --- | --- | --- |
| 小团队发起人 | 推动想法、协调方向 | 当前共识、实验比较、决策确认 |
| 开发成员 | 自由使用自己的工具实现方案 | 上下文包、任务状态、分享演示、追溯原因 |
| 体验与反馈成员 | 低门槛参与验证 | 一键打开演示、针对版本反馈、无需理解 Git |
| 暂时缺席的成员 | 快速恢复团队状态 | 变化摘要、已确认决定、来源引用与下一步 |
| 外部 AI 编程工具 | 按授权上下文执行具体开发 | 稳定机器接口、信息版本、可回传成果 |

### 3.2 权限模型

MVP 区分工作空间和协作空间两层成员权限，基本角色是所有者、成员和访客。确认正式决定的权限可以单独授予成员。默认不要求复杂的审批流程，但每次确认都要记下是谁操作的。

- 所有者：管理成员、协作空间配置、服务凭据、全局策略与删除/导出。
- 成员：讨论、会议、实验、演示、反馈；根据授权确认正式变更。
- 访客：在被明确邀请的范围内查看或反馈；默认不可访问全部历史与编程工具接口。
- 编程工具凭据：绑定人或服务账户、协作空间范围、最小读写权限、可撤销、可审计。

**授权和共识不同：** “某人可以修改记录”不等于“所有成员同意该方案”。需要争议处理的决定应标记为待讨论，而不是因为有操作权限就被包装成全体共识。

## 4. 产品信息架构与术语

### 4.1 一级导航

1. **协作空间：** 各项目或创意空间的入口。
2. **收件箱：** 对当前成员有意义的 @提及、待确认变更、重要阻塞与反馈。
3. **搜索：** 跨授权协作空间搜索消息、会议、决定、实验、演示和关联代码。
4. **设置：** 工作空间、权限、存储、AI、集成和数据导出。

### 4.2 协作空间内的工作区

| 区域 | 核心内容 | 主要交互 |
| --- | --- | --- |
| 概览 | 当前目标、有效决策、活跃实验、下一步、变化摘要 | 快速恢复 |
| 讨论 | 群聊、话题线程、引用、文件、@AI | 自由交流 |
| 会议 | 发起会议、屏幕共享、纪要、转录与时间点 | 开会和记录 |
| 探索 | 假设、实验分支、演示、反馈和结论 | 快速验证方向 |
| 计划 | 阶段目标、任务、依赖、阻塞和修订原因 | 由成员调整计划 |
| 上下文 | 决策、关系、知识来源、修订历史 | 查询当前已确认的内容 |
| 审核 | 待审核建议、批量确认与审核记录 | 集中整理 |

移动端早期以阅读、讨论、会议参与和反馈为主；复杂审核和开发工具操作优先适配桌面 Web。

### 4.3 文档里几个常用词

- **协作空间（Room）：** 一个项目或想法的长期讨论区，包含成员、权限、记录和项目资料。可以关联多个代码仓库，也可以没有仓库。
- **原始记录（SourceEvent）：** 消息、会议、Demo 反馈或代码事件本身，保留是谁、何时、在哪里产生的。
- **决策（Decision）：** 有权限的成员确认过的结论，有状态和修改历史。
- **实验（Experiment）：** 为了回答一个具体问题而尝试方案。同一目标可以同时做几个实验。
- **成果与预览（Artifact / Preview）：** 能拿来检查或体验的输出，如 Demo、构建、截图、录屏或报告；要有版本和访问范围。
- **任务（WorkItem）：** 要做的事、问题或阻塞，可以关联实验和决定。
- **计划（Plan）：** 当前目标、优先级、任务及其依赖，变动需要留记录。
- **上下文关联（ContextLink）：** 说明两条记录是什么关系，以及依据在哪里。
- **待审核建议（ChangeProposal）：** AI 或成员提出的修改，确认前还不是正式内容。
- **上下文修订（ContextRevision）：** 一次确认后保存的项目记录版本。
- **上下文包：** 按成员或编程工具的权限，整理出的项目背景和相关资料，带有版本号。

## 5. 几个实际使用场景

### 5.1 J1 · 从一个想法到两个 Demo

1. 发起人在协作空间内抛出一个不成熟的想法，成员自由讨论。
2. 大家明确当前需要验证的问题，例如“多人同时决策是否有趣”。
3. AI 从讨论中提出一项假设、两个实验方向与待确认行动项。
4. 成员在审核中编辑并确认实验，不要求把所有闲聊结构化。
5. 两位开发者分别使用自己的编程工具，通过 CLI 获取目标、约束和已确认决定。
6. 开发者发布两个可体验演示，关联实验与代码版本。
7. 其他成员打开演示、留下反馈；反馈固定关联到对应演示版本。
8. 团队比较体验，确认保留一个方向；计划与决策产生可追溯修订。

**完成标准：** 不依赖外部即时通讯工具；不同编程工具的开发者无需手动复制长篇聊天记录；团队能指出决定的原始依据与演示反馈。

### 5.2 J2 · 开完会后整理决定和待办

1. 成员在协作空间内发起语音会议，按需要共享屏幕；录制与转录需要明确告知和同意。
2. 会议期间可标记时间点或引用正在讨论的实验。
3. 会议结束后，成员可以基于人工纪要或已获同意的转录主动整理；启用 AI 且输入可用时生成可编辑摘要和建议决策、行动项、开放问题。未配置 AI 或转录时仍可手工完成。
4. 审核者检查待审核建议的来源片段与影响范围。
5. 审核者采纳、编辑、稍后处理或忽略；普通项目记录可批量确认，重大方向变更单独确认。
6. 确认后，协作空间的当前视图与编程工具上下文包更新；未确认内容保持建议身份。

### 5.3 J3 · @AI 协助突破僵局

1. 团队讨论两个方案都不理想。
2. 成员在当前线程 @AI，提出具体问题。
3. AI 在授权范围内获取本线程、当前决策、已有实验与反馈，给出分析、方案与证据引用。
4. AI 的回答是讨论消息，不会直接变成决策或修改计划。
5. 团队认可建议后，可以明确保存为待审核建议，或继续由后台提取等待审核。

### 5.4 J4 · 缺席成员与编程工具恢复

1. 成员进入协作空间概览，查看“自上次访问以来变化”。
2. 视图优先显示已确认的决定、实验状态、关键反馈、阻塞及仍未确认的重要提议。
3. 成员点击一项决定即可回到原始讨论或会议时间点。
4. AI 编程工具使用协作空间／实验标识读取上下文包，其中包含版本号、有效决策、任务范围与来源引用。
5. 如果上下文包已过期，客户端可以获取增量变化并提示成员重新检查有影响的工作。

### 5.5 J5 · 决策被推翻

1. 原决策 A 为“使用技术方案 X”。
2. 新讨论提出方案 Y；AI 识别出可能冲突，但不直接宣布 Y 生效。
3. 审核展示“拟替代决策 A”，附新旧内容、原始证据与影响对象。
4. 有权限成员确认后建立决策 B 和 supersedes 关系。
5. 普通搜索以 B 为当前有效决定，同时仍能查到 A 的历史原因。
6. 编程工具读取当前上下文不再把 A 当作有效约束；需要查根因时可沿来源继续展开。

### 6.1 FR-01 协作空间与成员管理

**优先级：P0**

- FR-01.1 创建、重命名、归档协作空间；协作空间拥有稳定标识、描述、成员与时区。
- FR-01.2 邀请成员、移除成员、设置所有者／成员／访客权限。
- FR-01.3 可选关联多个仓库或已有项目链接；不要求使用指定 Git 服务。
- FR-01.4 协作空间首页展示目标、活跃实验、最近确认变化、待审核数量和下一步。
- FR-01.5 默认仅协作空间成员可浏览记录；跨协作空间共享须明确授权。
- FR-01.6 删除或导出前显示影响范围，并保留合理的恢复策略。

**验收：** 新团队无需配置外部聊天账号即可创建协作空间、邀请成员并进行第一次讨论；访客无法读取未授权的私有内容。

<summary>FR-02 群聊与讨论</summary>

### 6.2 FR-02 群聊与讨论

**优先级：P0**

- FR-02.1 支持多人实时文本消息、基本 Markdown、代码块、文件附件、表情反应和 @提及。
- FR-02.2 支持回复线程、稳定消息链接、编辑与删除记录；引用失效时展示明确状态。
- FR-02.3 支持直接引用决策、实验、任务、演示与会议时间点。
- FR-02.4 支持消息搜索、未读定位、按话题查看以及与实验或任务关联。
- FR-02.5 @AI 在当前线程按需回答；不会未经邀请持续发送建议。
- FR-02.6 被删除或撤权的内容不得继续通过搜索、摘要或编程工具 API 泄露。

**P1：** 消息固定、话题分组、草稿同步、消息级原位建议预览。**P2：** 完整移动推送、高级富媒体和第三方 IM 导入。

**验收：** 成员可以在聊天中提及一个实验，另一成员能从该链接直达实验版本；@AI 回答附授权范围内的有效来源。

</details>

### 6.3 FR-03 内建会议与纪要

**优先级：P0 基础会议；P1 完整自动转录体验**

- FR-03.1 协作空间内发起或加入语音会议；MVP 面向少量成员设计，具有可见的参与者和麦克风状态。
- FR-03.2 MVP 支持屏幕共享和基础会议内文字记录；摄像头、多流布局和设备切换优化列为 P1。
- FR-03.3 会议拥有稳定 ID、标题、参与者、起止时间与关联协作空间。
- FR-03.4 会议纪要可人工编辑；具备转录能力时，按时间点关联原始转录证据。
- FR-03.5 录音、录屏与转录遵守明确同意、可见状态、可配置保留期与访问控制。
- FR-03.6 会议结束后可主动触发整理；可用的 AI 输入自动生成建议决策、行动项和开放问题，进入审核。
- FR-03.7 AI 不把不确定的说话人识别或模糊承诺自动转成已确认任务。

**降级要求：** 若 STT 尚不可用或服务失败，会议仍可正常开展，成员仍能手动记录与确认纪要；音视频能力不应依赖外部协作产品账号。

**验收：** 一次会议结束后，成员能形成可追溯的纪要和审核建议；没有同意录制的会议不会被后台悄悄录音。

</details>

### 6.4 FR-04 共享上下文与检索

**优先级：P0**

- FR-04.1 原始事件有稳定 ID、类型、作者或系统主体、时间、来源和权限范围。
- FR-04.2 保留当前有效决策、历史决策、实验结论、任务状态与计划修订。
- FR-04.3 检索支持关键词、对象类型、协作空间、时间、状态与来源筛选。
- FR-04.4 查询结果区分“已确认”“建议”“历史失效”“AI 推断”；不得混用。
- FR-04.5 内容之间的关联要记录关系类型、两端对象、创建人、依据、是否确认及是否失效。
- FR-04.6 支持通过对象关系回溯消息、会议时间点、代码引用及具体演示版本。
- FR-04.7 每个正式对象提供变更历史，并显示最新更新时间及确认人。

**P1：** 语义检索、相关路径逐步召回、跨多个协作空间的授权聚合。**P2：** 专用知识图谱引擎。

</details>

<details>
<summary>FR-05 项目记录的修改审核</summary>

### 6.5 FR-05 项目记录的修改审核

**优先级：P0，产品核心**

- FR-05.1 AI 可从群聊、会议、演示反馈与受信任集成事件中提取六类建议：决策、实验、任务、计划变更、开放问题、证据关联。
- FR-05.2 每条建议写明要改什么、建议内容、来源、证据片段、影响范围、所依据的版本和当前状态。
- FR-05.3 生成审核批次前，先筛掉不重要的内容，合并含义相近的建议，与当前记录比较，只保留需要改动的部分，并按话题分组。
- FR-05.4 在会议结束、讨论告一段落、积累了一批反馈或用户主动要求时整理建议，不要每条消息都弹窗。
- FR-05.5 对建议提供采纳、编辑后采纳、稍后处理、忽略和查看来源操作。
- FR-05.6 允许多条普通变更一次提交；替代正式决策、改变项目总体方向或授权范围的变更必须单独明确确认。
- FR-05.7 提交前展示修改前后有什么不同、会影响哪些内容、是否存在冲突，以及责任人是否还有未确认之处。
- FR-05.8 审核使用版本前提条件；基础版本失效时重新检查冲突并阻止静默覆盖。
- FR-05.9 确认写入新上下文修订，记录审核者、时间、变更集合与证据。
- FR-05.10 未确认建议不得混入当前有效决策；仅当调用方明确请求时才在独立字段或独立结果中返回，并明确标记为 pending。建议数量也须按当前调用方权限过滤。
- FR-05.11 支持重复建议合并、撤回错误建议、重开已暂缓项和确认后的修订；不可无痕篡改审计历史。
- FR-05.12 AI 故障时，成员仍可手动创建决策、实验与任务。

**验收：** 一场会议产生的多条有价值变化可集中审核；采纳后更新相关正式状态；忽略建议不会变成团队共识；冲突决策不能被自动替代。

</details>

<details>
<summary>FR-06 决策与当前共识</summary>

### 6.6 FR-06 决策与当前共识

**优先级：P0**

- FR-06.1 决策至少包含标题、结论、适用范围、状态、确认人、确认时间、来源证据和修订版本。
- FR-06.2 状态包含 proposed、active、superseded、revoked；被替代必须指向新的决定或说明撤销原因。
- FR-06.3 可由讨论、会议或实验结论创建；人工确认后方可 active。
- FR-06.4 同一个主题允许保留历史决定；默认查询当前有效版本，历史记录可明确展开。
- FR-06.5 决策影响已有任务和实验时，标记“需检查”，不得未经授权直接取消任务。

</details>

<details>
<summary>FR-07 实验与快速验证</summary>

### 6.7 FR-07 实验与快速验证

**优先级：P0**

- FR-07.1 可从讨论或审核创建实验；不要求预先生成 Jira 式任务清单。
- FR-07.2 实验记录假设、要回答的问题、判断标准、负责人、状态、建议方案、相关成果和反馈。
- FR-07.3 同一目标允许并行多个实验；实验之间可以比较，而不是强制串行。
- FR-07.4 状态包含 draft、active、evaluating、concluded、stopped；结论支持“支持假设”“不支持”“证据不足”。
- FR-07.5 结束实验不删除失败证据；可标注停止原因与再启动条件。
- FR-07.6 实验反馈可以转成建议决定、开放问题或任务，但未经确认不改变正式计划。

**验收：** 一个协作空间可以创建两个并行实验，分别挂载演示，收集体验反馈并形成可追溯的方向选择。

</details>

<summary>FR-08 演示、成果与体验反馈</summary>

### 6.8 FR-08 演示、成果与体验反馈

**优先级：P0 最小网页演示分享；P1 本地实时预览网关增强**

- FR-08.1 成果拥有稳定 ID、类型、版本、创建人、所属实验、时间、可见范围与来源说明。
- FR-08.2 MVP 支持登记现有 Web URL 或上传可访问的静态演示；无需推动整个团队先合并代码。
- FR-08.3 提供尽量简单的本地网页预览分享办法：由开发者 CLI 建立受控短期会话，生成可以撤销的链接。网络可行性验证前，不承诺不同网络下都能访问。
- FR-08.4 预览链接必须绑定某个明确运行实例或版本，展示创建时间、会话状态、失效时间与来源信息。
- FR-08.5 访客对具体成果版本发表评论；新版演示发布后，旧版反馈仍引用旧版本，不被自动迁移。
- FR-08.6 支持反馈转为建议问题、实验结论与任务；可引用截图或具体页面位置（P1）。
- FR-08.7 本地预览只暴露指定端口与资源；不得演变为任意命令执行代理或读取宿主其他文件。
- FR-08.8 访问权可按协作空间成员、单次邀请和到期时间限制；支持手动结束会话。

**P1：** 运行中演示版本快照、屏幕批注、自动附加 Git SHA 与工作区脏状态。**P2：** 非网页应用的可交互远程执行与通用桌面应用流化。

**验收：** 成员可以在不读取开发者本地代码的情况下访问授权演示，并对确切版本反馈；链接撤销后不再可用。

</details>

### 6.9 FR-09 计划与任务

**优先级：P0 轻量计划；P1 依赖与智能冲突检测**

- FR-09.1 计划展示目标、阶段、实验优先级、待办、阻塞、负责人和最近修订。
- FR-09.2 任务可独立创建或关联实验／决策；并非所有讨论都必须创建任务。
- FR-09.3 AI 可以推荐合并重复工作、调整优先级和识别依赖，但不得直接更改正式分工或取消任务。
- FR-09.4 计划修订要保留旧状态、变更原因、确认人和关联证据。
- FR-09.5 同时尝试几个方案时，要区分“还在验证的想法”和“已经承诺交付的任务”。
- FR-09.6 任务被分配给某人之前，应有可核实的接受状态；AI 不能根据模糊话语自动认定承诺。

- FR-10.4 能协助头脑风暴、提出实验方案、比较方案、发现计划冲突、总结下一步，但不能自动确认正式决定。

### 6.11 FR-11 外部编程工具接口

## 7. 建议怎么审核，决定怎么保存？

### 7.1 什么时候整理建议？

| 触发点 | 默认处理 | 打扰级别 |
| --- | --- | --- |
| 聊天持续进行 | 异步索引、聚合潜在变化，不逐条弹窗 | 静默 |
| 有人点击“整理本次讨论” | 生成当前线程的审核批次 | 用户主动 |
| 会议结束 | 在可用输入基础上生成纪要与建议 | 会议页面提示 |
| 演示收集一批反馈 | 合并重复反馈，提议问题或实验结论 | 探索页面提示 |
| 重要决策冲突被检测到 | 标为“可能冲突”，等待核查 | 协作空间内简短提醒 |
| 用户再次打开协作空间 | 展示与其有关的待办和确认变化 | 摘要，不强迫处理 |

不能因为“模型很确定”就自动采用一条建议。置信度可以用来排序或标出需要重点核对的内容，不能替代权限检查和成员确认。

### 7.2 一条建议要显示什么？

每张卡片固定呈现：

1. **建议操作：** 新增、更新、替代、撤销、关联或标记待检查。
2. **建议内容：** 简洁的人类可读陈述；避免长篇模型解释。
3. **前后差异：** 如果修改已有对象，明确展示修改前／修改后。
4. **证据：** 消息永久链接、会议时间戳、演示版本、Commit 等。
5. **影响范围：** 可能改变的决策、实验、计划、任务或编程工具上下文。
6. **可信状态：** 确认事实、AI 推断、存在歧义或与现有状态冲突。
7. **审核操作：** 采纳、编辑后采纳、稍后、忽略；具有权限时提交。

MVP 中来源必须可点击回到原始对象；当来源被删除、权限撤销或内容不可用时，卡片应显示“证据不可查看”，并提示来源已无法核对，不能显示成仍可查看的完整证据。

### 7.3 一次审核多条建议时

- 同一会议或同一话题生成一个主要批次，重复建议合并为一条并保留多处证据。
- 默认仅把用户明确选择的建议纳入提交；不提供暗含复杂影响的“全部自动通过”。
- 系统在提交前验证目标对象版本、权限和冲突。冲突须明确返回，不得把静默部分成功作为默认行为。整批拒绝或明确拆分提交、一次修订的提交单元和重试语义待 OD-12 确认。
- 如果一个批次包含重大决策替代，需单独展开前后对比并二次明确确认。
- “稍后”不会成为正式状态；有新证据时可以再次提醒，不能无限重复打扰。
- “忽略”表示不再反复提醒这条建议，不删除原始事件；新事实变化可以产生新的建议。
- 编辑建议需保留 AI 原建议与人工修改差异，最终以人工确认文本为准。

### 7.4 状态机

**待审核建议：** extracted → grouped → pending_review → accepted／edited_and_accepted／deferred／dismissed／superseded。只有 accepted 或 edited_and_accepted 会触发正式上下文修订。

**决策：** proposed → active → superseded／revoked。历史状态不可通过物理覆盖抹去；撤销、替代和修订均需记录原因。

**上下文修订：** 每个协作空间的正式上下文版本单调递增，记录产生时间、提交者、基础版本、变更对象列表与来源引用。并发审核须使用乐观并发控制或等价机制，拒绝覆盖更新。

### 7.5 看不准或有冲突时

- AI 不确定消息属于哪个实验时，建议进入未归属集合，显示可能匹配对象与证据，由成员选择；不得强制归档。
- 发言是建议、玩笑或反对意见时，不应默认识别为正式承诺。
- 会议摘要声称“全体同意”，但原始转录未能证明时，不允许将其作为无人核实的事实。
- 新旧决定冲突时，明确标记“讨论中”或“待替代确认”，不可依赖时间较晚就直接覆盖。
- 多成员同时审核时，已失效建议需刷新并重新确认。
- 不能访问证据的访客或编程工具不应通过建议摘要间接获取超出授权的信息。

### 7.6 确认之后显示什么？

提交后展示：已更新的对象、正式版本、尚待处理的冲突、可撤销／修订入口。关联成员只接收与其行动有关的精简变化摘要；不要求所有成员重新阅读整个会议纪要。

## 8. 页面怎么安排？

### 8.1 协作空间概览

默认首屏回答“我们在做什么、最近什么变了、接下来做什么”。建议布局：

- 顶部：协作空间名称、目标、成员、会议入口、创建实验按钮。
- 主区：当前有效决策（少量）、活跃实验与演示、下一个重要行动。
- 侧区：自上次访问的正式变化、需要本人处理的审核和 @提及。
- 深入入口：完整讨论历史、上下文关系、旧决策和归档实验。

如果协作空间还没有正式决定，显示“暂无已确认决策”；建议在独立区域标明“待审核”，不得称为已有共识，也不得让 AI 虚构一份项目目标。

### 8.2 讨论

聊天为默认日常入口；成员可自然发送消息。在消息旁提供“转为实验／决策建议”“引用到任务”“提及 AI”等操作，不要求每次发言都选择内容类型。长讨论可以按线程折叠；AI 的后台发现以不打断讨论的标记呈现。

### 8.3 审核收件箱

按协作空间、来源批次、变更类型和风险显示建议。列表只展示变更摘要；点击展开差异、原始证据及影响范围。桌面端支持多选批量提交、键盘快速审核与修改草稿；移动端先保证单条审核可用。审核者不需要阅读整段转录才能确认每个建议；来源存在且仍有访问权限时可以回看，否则显示来源不可用状态。

### 8.4 探索

以“正在验证的问题”为一级标题，展示多个并行方向。每个实验卡片有假设、负责人、状态、演示、最近反馈与结论。比较视图优先展示体验证据和判断标准，而非只比较代码完成度。

### 8.5 演示反馈

访问者始终看到自己正在体验的版本标识和更新时间。反馈输入靠近演示，支持文本和基础评分／观察类型（例如有效、困惑、缺陷）；反馈提交后固定关联版本。实验负责人可以批量查看、归类并转成建议问题。

### 8.6 计划

默认精简的阶段目标与任务列表，不强制 Scrum 流程。变更视图显示“此前 → 当前”和原因；对 AI 提出的重排或冲突建议提供审核入口，而非悄然改动卡片位置。

| DiscussionThread | id、room_id、root_event_id | 聊天上下文和回复关系 |
| Meeting | id、room_id、started_at、ended_at、consent_state | 记录会话及转录范围 |
| Decision | id、room_id、text、status、version、approved_by | 正式结论的生命周期 |
| Experiment | id、room_id、hypothesis、criteria、status、owner | 验证问题而非默认交付任务 |
| WorkItem | id、room_id、scope、status、assignee、accepted_at | 轻量任务及责任状态 |
| PlanRevision | id、room_id、before_ref、after_ref、approved_by | 计划可回溯 |
| Artifact | id、experiment_id、kind、version、source_ref、access_policy | Demo 与反馈的稳定目标 |
| Feedback | id、artifact_id、author、body、created_at | 不跨 Demo 版本误绑定 |
| ContextLink | source、target、relation、evidence、status、created_by | 类型化证据关联 |
| ChangeProposal | id、operation、target、base_version、proposal、evidence、status | 未确认的结构化变化 |
| ReviewBatch | id、room_id、proposal_ids、reviewer、status | 组织审查但不等于生效 |
| ContextRevision | id、room_id、base_revision、changes、actor、timestamp | 正式状态变更日志 |
| AgentCredential | id、subject、scopes、expires_at、revoked_at | 最小权限与审计 |

这只是关键字段示意，不是完整数据库或接口定义。

Feedback 必须指向当时体验的确切成果版本。如果 artifact_id 本身就代表一个不可变版本，单独引用它才足够；否则还需要版本信息。消息等来源也要能指向被引用时的内容，避免原文编辑后，旧证据跟着变化。

具体怎样表示，在 OD-13 中确认。

逻辑模型不要求一张表对应一个实体。初期可采用关系数据库与对象存储；可检索文本、文件及媒体索引在权限与保留策略下构建。所有对象使用不可复用的稳定 ID，避免引用因重命名或位置移动失效。

### 9.2 上下文关联关系集合

首版先支持以下含义明确的关系：discusses、proposes、decided_in、supersedes、implements、demonstrates、verified_by、feedback_on、blocks、relates_to。

关系有两种不同可信状态：explicit／confirmed（用户明确建立或确认）和 inferred（AI 推断）。例如，“Commit 修改了相关文件”并不自动证明“Commit 实现了某项决策”；implements 应有人的确认或可信工作流证据。

### 9.3 分领域事实来源

| 领域 | 权威来源 | Demble 维护的内容 |
| --- | --- | --- |
| 聊天与会议 | 原始消息、音视频／转录记录 | 索引、引用、纪要与提取建议 |
| 代码历史 | Git 仓库与 Commit | 代码引用及其与实验的关系 |
| 团队正式决定 | 已确认的决策修订 | 当前有效视图、替代关系与证据 |
| 编程工具私有执行 | 各自编程工具／本地环境 | 经用户授权回传的结果与会话引用 |
| 演示体验 | 对应成果的具体版本 | 访问、反馈、版本与来源关系 |

AI 摘要不能代替这些原始资料。例如，代码做了什么应以 Git 记录为准，团队决定了什么应以确认记录为准。

### 9.4 删除、修正与可追溯性

对原始事件的删除或权限撤销要传播至索引、缓存和衍生检索结果；对于已依据该事件形成的决策，保留“曾有引用但来源已不可见”的审计事实，同时限制敏感原文继续传播。正式决策可通过修订或撤销纠错，而不是悄悄修改旧版本。备份与保留期遵循协作空间配置和法律／团队约定，不能承诺一切数据永不删除。

</details>

## 10. 编程工具接口约定

### 10.1 设计原则

CLI、HTTP API、未来 MCP 适配器共用一套鉴权与领域内含义。客户端不应依赖网页 DOM、特定模型提示词或内部数据库字段。响应中的记录要有稳定 ID、数据版本和更新时间，并说明权限过滤结果；请求失败时返回清楚的错误信息。

### 10.2 建议命令

以下是需求层面的示例，不表示这些命令已实现，也不表示 CLI 名称或参数已确定：

~~~bash
room auth login
room room list --json
room context pack --room game --experiment EXP-B --json
room context changes --room game --after-revision 27 --json
room decision list --room game --status active --json
room experiment show EXP-B --json
room artifact publish --experiment EXP-B --url https://demo.example.test --json
room progress report --work-item TASK-34 --commit a1b2c3 --json
room preview share --room game --experiment EXP-B --port 3000
~~~

### 10.3 上下文包样例

~~~json
{
  "schema_version": "0.1",
  "room_id": "game",
  "context_revision": 28,
  "generated_at": "2026-11-02T10:00:00+08:00",
  "scope": {"experiment_id": "EXP-B"},
  "goal": "验证多人实时互动是否有趣",
  "current_decisions": [
    {"id": "DEC-19", "version": 1, "text": "优先验证多人互动",
     "evidence_refs": ["meeting:8@24:18"]}
  ],
  "superseded_decisions": [{"id": "DEC-12", "superseded_by": "DEC-19"}],
  "work_items": [{"id": "TASK-34", "status": "needs_review"}],
  "open_questions": [{"id": "Q-8", "text": "同步机制如何简化"}],
  "artifacts": [{"id": "ART-7", "version": 2, "experiment_id": "EXP-B"}],
  "pending_change_count": 2,
  "source_links": {"DEC-19": ["meeting:8@24:18"]}
}
~~~

这份 JSON 只用于说明概念。错误格式、分页、版本引用和权限失效后的行为还没定。

权限检查要覆盖每个字段，包括来源链接、历史决定、成果和待处理数量，不能只过滤 current_decisions。

正式上下文和未确认提案必须以不同字段或调用结果表达。默认返回的上下文包不能把 pending 状态的建议当成需要执行的要求。调用方可明确请求待讨论信息用于分析，并显示其状态。

### 10.4 写入与执行边界

编程工具或 CLI 可以在授权范围内提交成果、进展、测试证据和待审核建议。

写入正式决定、修改计划或分配任务时，仍须检查对应用户的权限并走确认流程。如果以后引入自动执行工具的系统，必须另外讨论。允许执行的范围要单独授权，不能因为有一条团队决定，就自动获得执行权限；服务端和执行工具都要检查。这不属于当前核心 MVP。

### 10.5 同步与一致性

每个读取响应返回当前 context_revision。编程工具在执行前可记录基础版本，在报告成果时附带该版本；若重要决定在其运行期间变更，协作空间应显示“可能基于过期上下文”，并提供 changes 增量。系统不试图远程篡改外部编程工具当前会话。

context_revision 记录的是已确认项目内容的版本，不是访问许可，也不能代表整个响应的缓存版本。

每次请求都要检查当前成员资格、凭据权限和撤销状态。即使修订号没变，也不能直接复用旧权限下的结果。权限、来源删除、成果和建议数量变化时，缓存及增量结果怎样更新，待 OD-11 确认。

服务端必须停止后续未授权访问，并清理自己控制的副本；已经交给外部客户端的数据，不能承诺可以远程收回。

## 11. 非功能需求

<details>
<summary>查看部署、性能、可靠性、安全和无障碍要求</summary>

### 11.1 部署与可维护性

- **NFR-01 自托管：** 提供明确安装、升级、备份与恢复路径；日常使用无需第三方协作平台账号。
- **NFR-02 可配置 AI：** AI 模型服务通过适配器配置，提供不开启 AI 时的基础手工工作流；模型不可用不应阻断聊天与会议。
- **NFR-03 开放接口与互操作：** 核心协议与数据导出格式有文档；避免以单一编程工具 SDK 作为领域模型。
- **NFR-04 可迁移数据：** 支持按协作空间导出标准结构化记录、附件索引和引用关系；导出需权限校验。
- **NFR-05 小团队优先：** 首个部署目标是 2–10 名成员，不为了假想的万人规模引入过度分布式架构。

### 11.2 建议的初期体验预算

以下为设计目标，需通过原型测试校准，非已实现承诺：

| 指标 | MVP 目标 |
| --- | --- |
| 实时消息体感 | 在常见家庭／校园网络下稳定、低延迟；测量发送到可见时间 |
| 协作空间概览 | 常规数据量下首屏主要信息在 2 秒左右可交互 |
| 关键词检索 | 常规协作空间的典型查询在 2 秒左右返回首批结果 |
| 上下文包 | 常规范围读取在 3 秒左右返回，不含外部模型生成时延 |
| 审核批次 | AI 处理异步进行，用户可离开；有进度、失败重试和人工兜底 |
| 演示分享 | 已启动的受控分享会话应在短操作路径内获得链接 |

这些数值将基于设备、网络、协作空间数据量与自托管资源设定正式 SLO；不把 AI 响应速度与确定性 API 的延迟混为一谈。

### 11.3 可靠性、审计与恢复

- 审核提交采用原子更新或明确的部分失败补偿策略；不能出现“界面显示成功但正式上下文只更新一半”。
- 消息发送、AI 提取、编程工具进展上报与反馈接收须考虑重试、幂等和去重。
- 重要状态变更有审计日志，至少记录主体、对象、操作、前后版本与时间。
- 支持日常备份与恢复演练；原始媒体大文件与结构化数据库的恢复一致性要测试。
- 会议媒体故障与 AI 服务故障不得导致已保存聊天或正式决策丢失。

### 11.4 安全与隐私

- 强制鉴权、协作空间级授权和对象访问检查；搜索、预览、上下文包、来源回溯与 AI 检索都使用同一权限边界。
- 服务端密钥和编程工具令牌不进入聊天文本或公开演示；令牌可限定作用域、到期与撤销。
- 共享演示使用临时、可撤销授权，不直接暴露开发者文件系统或本地管理接口。
- 对聊天、会议、附件及代码片段的 AI 处理提供数据流向说明和配置；默认不将私有本地代码自动上传。
- 记录／转录时参与者可见状态与同意管理；没有权限的转录不会进入搜索或 AI 上下文。
- 防御来自聊天、文档、网页和演示反馈的提示注入：把这些内容视为数据，不允许它们改变服务端权限或编程工具写入范围。
- 审核、AI 输出、导出和删改操作留下适当的审计信息，同时避免审计系统泄露敏感原文。

### 11.5 可访问性与国际化

桌面 Web 需支持键盘操作、焦点可见、基础屏幕阅读语义和明确状态文本；关键状态不能只用颜色区分。首版以中文为主，数据模型、日期和 UI 文案预留国际化能力。

</details>

## 12. MVP 计划与阶段性交付

### 12.1 S0：先让三个人用起来

做成员邀请、项目空间、实时聊天、消息引用、语音会议、屏幕共享和手工纪要，先不接 AI。

完成时，三个人应当能独立完成一次讨论和会议，不需要外部协作账号。消息和会议有稳定 ID，成员隔离已经通过测试。

### 12.2 S1：把讨论整理成有依据的决定

支持手工创建决定，以及原始记录、内容关联、AI 待审核建议、去重、批量审核、版本记录和当前内容检索。

完成时，一次讨论或会议能经过成员确认形成决定；旧决定被替换后，不会继续作为当前要求返回；成员能打开相关来源核对。

### 12.3 S2：做出两个方案，拿来比较

加入实验、简单计划、成果和版本反馈，先支持网页 URL 与静态 Demo。同时验证本地预览分享的网络和安全限制。

完成时，两位开发者提交两个可体验的方案。反馈要记在正确版本上，实验结论经审核后能够更新计划。

### 12.4 S3：接上不同的编程工具

提供 CLI、HTTP API、上下文包、context_revision、权限令牌，以及少量进展和成果提交接口。工具基于旧项目背景工作时，要提示可能过期。

完成时，至少两种 AI 编程工具在相同权限下读到一致的有效决定。未确认建议不会被当成正式要求，成果也能关联到对应实验。

### 12.5 S4：让日常使用更省事

连续两周真实使用后，再改进变化摘要、去重、讨论整理、@AI、搜索、转录、性能和故障恢复。

完成时，团队能记录恢复项目进度和处理审核各花了多少时间，并据此决定下一步要改哪里。

### 12.6 各项能力先做到什么程度

| 能力 | MVP 先做 | 后续增强 | 暂不做 |
| --- | --- | --- | --- |
| 聊天 | 实时文本、线程、引用、附件 | 高级通知、消息整理 | 通用社交功能 |
| 会议 | 语音、共享、手工纪要，AI 整理可选 | 自动转录、回放、视频优化 | 大规模会议平台 |
| 审核 | 建议、去重、批量确认、版本记录 | 更细的冲突检查 | 自动替团队作决定 |
| 实验 | 假设、多方案、结论、反馈 | 模板和体验比较 | 自动研究和调度 |
| Demo | URL、静态成果、按版本反馈 | 完善受控本地动态预览 | 通用远程桌面 |
| 编程工具 | CLI、API、项目资料读取和成果提交 | MCP、订阅 | 托管长期运行的执行工具 |
| 计划 | 成员维护，修改有记录 | AI 建议依赖和冲突 | 自动执行计划 |

这些阶段按验证需要排序，尚未估算固定工期。会议和本地动态预览都需要尽早验证网络及安全限制，可以先复用成熟组件、简化功能，但不能因此直接删去产品目标。

## 13. 怎么判断产品有没有帮助？

<details>
<summary>查看试用方法和需要测量的指标</summary>

### 13.1 需要记录哪些变化？

我们要看的是：团队把想法做成可体验的结果时，花在找资料、同步状态和重复解释上的时间有没有减少。

| 指标 | 定义 | 如何采集 |
| --- | --- | --- |
| 从想法到演示的时间 | 从创建实验／明确想法到首个可体验版本的时间 | 实验与成果时间戳 |
| 上下文恢复成本 | 缺席成员或新编程工具恢复正确状态的人工解释次数与耗时 | 任务观察、访谈、操作日志 |
| 协调开销 | 用于寻找资料、同步状态、搬运上下文和确认分工的额外操作 | 观察记录与用户反馈 |
| 审核耗时 | 每个审核批次的有效处理时间 | 审核交互事件 |
| 建议采纳率 | 建议被采纳的比例，分类型观察 | 待审核建议状态 |
| 重大修正率 | 建议在事实、责任人或状态上需重大修改的比例 | 审核前后差异 |
| 上下文正确性 | 被询问的当前有效决策及其证据是否准确 | 人工抽样与场景测试 |
| 演示反馈周期 | 每个实验获得反馈、形成结论并更新计划的周期 | 实验、反馈与修订时间 |

不能只追求提取更多建议或提高采纳率。模型可能通过少提建议提高采纳率，因此需结合漏提、错误归档、人工修正与信息恢复正确率综合判断。

### 13.2 试点计划

邀请 3–5 位同学，用一个方向还没完全确定的真实项目试用至少两周。先记录使用现有工具时，做 Demo、找回项目进度和整理会议各要花多久。

试用中记录失败的例子：AI 总结错了、建议反复出现、Demo 打不开，或成员不知道为什么没有权限。之后按这些实际问题和成果质量决定下一轮开发内容。

### 13.3 需要通过试用回答的问题

1. 团队愿意把真实日常讨论放在 Demble，而不仅把它当成存档网站。
2. AI 建议审核比人工总结更省时间，并且不会引入不可接受的错误。
3. 开发者愿意从 CLI 读取上下文并回传成果，即使使用不同编程工具。
4. 演示版本关联和原位反馈能显著缩短方向决策周期。
5. 自托管会议与聊天的维护负担不会抵消上下文整合带来的收益。

</details>

## 14. 验收用例

<details>
<summary>查看 18 项验收场景</summary>

**AT-01 · 协作空间成员隔离**

访客无权限时，不能通过页面、搜索、API 或 AI 得到私有消息与决策

**AT-02 · 群聊引用**

两位成员发送、回复并引用实验；引用能定位稳定对象与具体版本

**AT-03 · 会议纪要**

会议结束后能生成可修改纪要，明确区分原始讨论与正式确认项

**AT-04 · 批量审核**

多条普通建议一次确认后，相关对象一致更新并生成上下文修订

**AT-05 · 重大决策**

一条取代当前架构方案的建议不能在普通批量操作中无提示生效

**AT-06 · 并发冲突**

两名成员基于同一旧版本修改同一决策，后提交者收到冲突提示

**AT-07 · 错误 AI 提取**

将一句玩笑识别为任务时，审核者可忽略且不会分配正式责任人

**AT-08 · 决策替代**

决策 B 替代 A 后，默认查询返回 B；A 保留历史与 supersedes 链

**AT-09 · 实验比较**

一个目标下有两个活跃实验与各自演示；反馈和结论可按版本筛选

**AT-10 · 演示撤销**

分享链接到期／被撤销后不能再访问；反馈仍保留正确版本关联

**AT-11 · 编程工具一致性**

两种编程工具使用相同接口约定读取当前 context_revision 与有效决定

**AT-12 · 编程工具过期**

编程工具基于旧版本提交结果时，系统提示可能与最新决定不一致

**AT-13 · AI 降级**

AI 服务失效时，手工聊天、开会、创建决策及搜索仍可使用

**AT-14 · 来源删除**

来源被撤权后，搜索和上下文包不应泄露原文，引用状态明确

**AT-15 · 录制同意**

未获得录制许可时，不进行隐藏录音或把会议音频发往模型服务

**AT-16 · 用户恢复**

缺席成员能从概览找到最近正式变化及每条的来源

**AT-17 · 错误责任归属**

AI 推断某人负责任务时，未获得本人或有权人的确认前不标记已接受

**AT-18 · 恶意提示内容**

用户消息或演示反馈不能通过提示注入绕过读写权限或自动执行命令

</details>

## 15. 主要风险与缓解

| 风险 | 影响 | 缓解策略 |
| --- | --- | --- |
| 群聊使用率不足 | 无法积累自然上下文 | 先用真实朋友团队验证每日沟通便利性，降低加入和讨论门槛 |

| 权限与来源删除处理不完整 | 信息泄露或审计失真 | 全链路鉴权、衍生索引撤权传播、审计和恢复测试 |

## 16. 还没决定的问题

下面都是待讨论事项，不是已经批准的方案。可以先做原型；涉及权限、正式写入和数据保存的规则，要在对应阶段开始实现前说清楚。

OD-11–OD-14 在[任务 #12](https://github.com/demble-team/demble/issues/12)集中跟踪。

### 成员、权限和责任

**OD-01 · 谁能确认团队决定？**

建议由 Owner 配置哪些成员有确认权。需要在权限设计和审核页面中表达清楚。

**OD-02 · 重大分歧要几个人确认？**

建议首版不强制投票，但要显示有争议的地方，并要求明确处理。具体规则仍需团队讨论。

**OD-08 · 编程工具提交什么可以不用逐条审核？**

建议只允许直接记录少量实际进展和成果信息。正式决定和计划仍须确认，哪些上报会改变任务状态也要说清楚。

**OD-09 · 不同项目空间能共享哪些资料？**

建议默认不互通。跨空间引用需要明确授权，搜索和索引也应遵守相同规则。

**OD-14 · 有权安排任务的人，能否替成员接受任务？**

“已经分配”和“本人已经接受”不能混为一谈。是否允许代接受、谁能操作、状态怎样记录，还需要确定。

### 会议、Demo 和部署

**OD-03 · 首版会议要支持摄像头吗？**

建议 P0 先做语音和屏幕共享，视频优化放到 P1，避免一开始承担过多音视频开发工作。

**OD-04 · 没有语音转文字，首版能发布吗？**

建议可以。先保证会议和手工纪要可用；没有转录或 AI 时，也要能继续讨论、整理和确认。

**OD-05 · 首版要能分享本地运行的 Demo 吗？**

建议先验证网络和安全可行性。MVP 保证现有 URL 和静态 Demo 可用，本地动态分享紧接着增强。

**OD-06 · 最先支持哪种部署环境？**

建议先支持单机 Linux 和容器，其他平台随后验证；具体安装和维护办法还没确定。

**OD-07 · 默认使用云端模型还是本地模型？**

建议允许配置，并在发送私人资料前取得授权。默认选项仍需结合隐私、费用和性能讨论。

**OD-10 · 首版要深度接入 GitHub 或 Gitea 吗？**

建议先用代码链接和 Commit 引用，不依赖某一个 Git 服务，之后再看是否值得做更深的集成。

### 记录、版本和提交

**OD-11 · 权限、来源或成果变了，但正式版本没变，上下文包什么时候失效？**

每次请求都要重新检查当前权限。除此之外，缓存如何更新、哪些变化能增量读取、接口需要哪些字段，留给数据和权限设计确认。

**OD-12 · 一批建议中有冲突，是全部退回，还是让用户拆开提交？**

不能只保存一部分却显示全部成功。一次提交包含哪些内容、生成几个版本、失败后怎么重试，还没有定。

**OD-13 · 消息被改过、Demo 更新过，怎样引用当时的确切版本？**

反馈必须对应当时体验的成果版本，证据必须对应当时引用的内容。用什么标识、删掉后显示什么，需要在来源和成果设计中确认。

## 17. 从哪里开始，做到什么程度？

### 17.1 建议从这里开始

1. 先讨论协作空间、原始记录、决定、实验、待审核建议和版本记录各表示什么，谁能读写。
2. 先把手工聊天、安排实验和记录决定的流程做好，再接 AI 整理。
3. 用一次“讨论 → 提出建议 → 成员确认 → 保存决定”的完整过程验证审核功能，再接会议和 Demo。
4. 找两种不同的编程工具，检查它们读到的项目资料是否一致。
5. 分别验证会议和本地预览的网络、安全与使用体验，再接到主流程里。
6. 请真实小团队试用，根据实际问题决定后续工作。

### 17.2 MVP 做到什么才算完成？

一组真实成员能在自己部署的项目空间里讨论和开会，把带来源的建议确认成决定，并尝试两个不同方案。其他成员能打开 Demo，按版本留下反馈，再据此调整计划。

至少两种 AI 编程工具能读取最新且有权访问的项目资料。团队可以在方案变化后找回当前决定，不用再手工复制大段聊天记录。

未确认的 AI 建议不能显示成正式决定。权限、来源和版本相关验收要通过测试。P2 功能不作为 MVP 完成的条件。

### 17.3 以后再考虑的功能

先验证基本协作有没有帮助，再考虑更好的会议转录、Demo 快照和批注、上下文增量订阅、计划冲突提示及跨空间关联。

如果以后确实需要编程工具的自动执行和调度，应单独讨论，并放在外部运行系统中。Demble 仍负责团队协作和项目资料，不接管成员的编程会话。

## 附录 A 产品需求核对清单

- [ ] 不依赖外部即时通讯工具完成基本群聊与会议。
- [ ] AI 默认静默，成员 @AI 时才主动参与讨论。
- [ ] 决策与任务确认由有权的人完成，不由 AI 悄悄生效。
- [ ] 原始事件、AI 建议、正式知识和当前工作视图严格区分。
- [ ] AI 建议具有来源、影响范围、去重和批量审核机制。
- [ ] 决策可以被修订、替代与撤销，历史仍可查询。
- [ ] 一个想法可以并行验证多个实验。
- [ ] 演示、反馈、代码来源与具体版本可关联。
- [ ] 不同编程工具通过统一机器接口获得相同语义的上下文。
- [ ] 重要的权限边界在 Web、API、搜索和 AI 检索中一致。
- [ ] 成员缺席后能够按增量快速恢复，不必阅读完整历史。
